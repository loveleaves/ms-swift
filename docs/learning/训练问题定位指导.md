# ms-swift GRPO 训练问题定位与修复技术报告（通用场景版）

> 覆盖场景：GRPO + LoRA（colocate/server）、GRPO + 全参数（Full）、GRPO + 多机多卡分布式、GRPO + 多模态（VL）、GRPO + Megatron-swift 大规模并行。
> 以"训练能跑通但 loss/reward 等核心指标异常（尤其是恒为 0）"为主线问题，兼顾 OOM、卡死、速度异常等强相关的伴生问题类型。

---

## 第一部分：通用方法论（适用于所有 GRPO 训练场景）

### 1.1 GRPO 训练的计算链路

无论 LoRA 还是全参数、单机还是多机，GRPO 的核心计算链路都是四段式的，这是所有排查的起点：

1. **Rollout（采样）**：当前策略模型对一批 prompt 各生成 `num_generations` 个 completion。采样可以走原生 `transformers.generate`（`use_vllm=false`），也可以走 vLLM 加速（`use_vllm=true`，再分 colocate / server 两种部署形态）。
2. **Reward 计算**：由 `reward_funcs`（内置 accuracy/format，或 `--external_plugins` 注册的自定义函数）和/或 `reward_model` 对 completion 打分。
3. **Advantage 归一化**：以"生成组"（同一 prompt 的 `num_generations` 个样本）为单位做组内标准化：`advantage = (reward - group_mean) / (group_std + eps)`。
4. **Loss 计算**：基于 advantage 与新旧策略概率比构造 clipped policy loss；`beta > 0` 时叠加与参考模型的 KL 惩罚。

**这条链路是排查一切"指标异常"问题的坐标系**：任何时候看到某个指标异常，先问"它在链路的第几步"，再决定往哪个方向排查，而不是直接怀疑框架有 bug。

### 1.2 关键诊断指标一览

ms-swift 在训练日志中输出了大量诊断性指标，很多人只盯着 `loss`/`reward` 两个顶层数字，导致排查效率低。建议排查时按下表逐项核对：

| 指标 | 含义 | 异常时提示的问题层级 |
|---|---|---|
| `reward` / `rewards/{func_name}/mean` | 各奖励函数的平均得分 | reward 恒为 0 → 生成内容或奖励函数本身 |
| `reward_std` | batch 内 reward 的标准差 | 长期为 0 → 组内无区分度 |
| `frac_reward_zero_std` | 组内 reward 标准差为零的样本占比 | 接近 1 → advantage 大面积坍缩为 0，直接导致 loss≈0 |
| `kl` | 策略与参考模型的 KL 散度（仅 `beta>0` 时记录） | `beta=0` 时恒为 0 是**预期行为**，不是 bug |
| `clip_ratio/*` | 被 PPO-clip 机制截断的 token 比例 | 全 0 或异常大，提示 ratio 计算/权重同步异常 |
| `completions/mean_length`、`min_length`、`max_length` | 生成长度统计 | 长度恒定或极短，提示生成退化 |
| `grad_norm` | 梯度范数 | 恒为 0 但 reward 正常，提示反向传播/参数挂载问题，而非 reward 问题 |
| `completions/clipped_ratio` | 因长度截断被丢弃的样本比例 | 过高提示 `max_completion_length` 设置不合理 |

**核心判断法则**：
- `reward=0` 且 `loss=0` 同时出现 → 问题在链路上游（生成或奖励函数），顺藤摸瓜往前查（对应本报告第三部分案例）。
- `reward` 正常但 `loss=0` → 先看 `frac_reward_zero_std`，大概率是组内无区分度（数据难度/采样多样性问题），不是 bug。
- `reward` 正常、`loss` 正常，但 `grad_norm=0` → 问题在优化器/参数挂载层，与 reward/loss 计算无关（LoRA 场景尤其要重点检查这条）。
- `kl=0` 且已知 `beta=0` → 正常现象，无需排查。

### 1.3 通用分层排查框架

| 层级 | 排查内容 | 关键手段 |
|---|---|---|
| L0 环境/版本层 | ms-swift、transformers、trl、vllm、deepspeed 版本组合是否为已知可用组合 | 查官方 release notes / GitHub issue 按版本号搜索 |
| L1 数据层 | 数据集字段是否与 reward 函数期望字段对齐；预处理后的实际内容 | 打印数据集前几条、脱离训练单独跑一遍预处理逻辑 |
| L2 采样(rollout)层 | 真实生成内容是否正常；vLLM/transformers 后端是否正确加载权重 | `--log_completions true`，直接看生成文本 |
| L3 奖励函数层 | reward 函数单独调用是否符合预期 | 单元测试，构造已知样本手工验证 |
| L4 Advantage/Loss 层 | 组内方差、KL、clip_ratio 是否正常 | 核对 `reward_std`、`frac_reward_zero_std`、`kl` |
| L5 优化器/参数层 | LoRA/全参数是否真正参与反向传播；deepspeed/FSDP 配置是否兼容 | 核对 `grad_norm`、`requires_grad`、`target_modules` |
| L6 分布式/权重同步层（多机、vLLM colocate/server 特有） | 训练权重是否正确同步到推理引擎；多进程/多节点通信是否正常 | 对比训练前后 vLLM 生成内容是否变化；核对同步日志 |
| L7 日志/显示层 | 是否为打印口径、`logging_steps`、梯度累积导致的"假异常" | 对照官方文档中各指标的统计口径 |

**排查原则**：最小化复现（缩小 batch/generation 规模）→ 单变量控制 → 优先看框架已暴露的诊断指标，而非仅凭 `loss`/`reward` 两个数字下结论。

## 第二部分：分场景专题分析

同样是"loss/reward 异常"，在不同训练形态（LoRA/Full）、不同部署形态（单机/多机、colocate/server）、不同模型形态（纯文本/多模态）、不同并行框架（Transformers-based/Megatron-swift）下，根因分布和排查重点显著不同。以下逐场景展开。

### 2.1 场景一：GRPO + LoRA（单机，最常见入门场景）

**特点**：只有 adapter 参数参与训练，显存压力小，最容易上手，但也引入了 LoRA 特有的两个"额外环节"：LoRA 是否真正参与前向/反向、以及（若用 vLLM 加速）LoRA 权重是否正确同步到推理引擎。

**与全参数训练相比的关键不同点**：

1. **权重同步方式不同**：全参数训练时，vLLM 侧同步的是完整模型权重；LoRA 训练时，可以选择"仅同步 LoRA adapter 权重"（`vllm_enable_lora true`）而不必每次同步整份底座权重，这样速度更快，但要求 `vllm_max_lora_rank` 必须与训练脚本的 `lora_rank` 保持一致，否则同步会静默失败或效果异常。
2. **多模态 ViT 层的例外情况**：若训练同时打开了多模态模型 ViT 层的 LoRA（`freeze_vit false`），"仅同步 LoRA"这一优化路径不支持这种情况，需要相应在 vLLM 侧开启 tower/connector 的 LoRA 支持，否则会出现视觉塔权重未同步、生成内容与训练权重不一致的问题。
3. **`grad_norm` 异常是 LoRA 场景的高发问题**：由于只有极少量参数（adapter）参与训练，一旦 `target_modules` 配置遗漏关键层，或 adapter 未正确挂载到计算图上，`grad_norm` 会长期为 0，但此时 reward 通常是正常的——这与"reward=0"是完全不同性质的问题，注意区分。
4. **合并（merge）与推理一致性问题**：训练过程中若涉及阶段性 `--adapters`/`--ref_adapters` 加载（如二阶段 GRPO），需要确认 adapter 路径、`ref_adapters` 是否指向正确的 checkpoint，二阶段衔接时的 KL 基线设置错误会导致 KL 从不合理的数值开始爬升。

**LoRA 场景专属排查清单**：
- [ ] `lora_rank`（训练侧）与 `vllm_max_lora_rank`（vLLM 侧，若开启 `vllm_enable_lora`）严格一致
- [ ] 若多模态且 ViT 层开启 LoRA，未使用"仅同步 LoRA"优化路径，或已确认 vLLM 侧支持 tower/connector LoRA
- [ ] `target_modules` 覆盖了实际需要训练的层（尤其是自定义模型结构时不要照抄默认配置）
- [ ] `grad_norm` 非 0（若为 0，先排查这条，而不是去查 reward 函数）
- [ ] 二阶段/多阶段训练时 `adapters` 与 `ref_adapters` 指向正确、KL 基线符合预期

### 2.2 场景二：GRPO + 全参数（Full）训练

**特点**：全部参数参与训练，显存与通信压力显著高于 LoRA，因此该场景下的"异常表现"往往不是 loss/reward 为 0，而是 **OOM、卡死、速度异常**，其次才是指标异常；即便是 loss/reward 异常，往往也与显存不足导致的静默降级（如生成被截断、被跳过）有关联。

**与 LoRA 场景相比的关键不同点**：

1. **OOM 是全参数训练最高发的问题类型**，尤其是叠加 vLLM 做 rollout 加速时：训练进程（保存优化器状态、梯度）与推理进程（vLLM KV cache）需要共享/竞争显存。官方给出的核心优化手段包括：
   - `--sleep_level 1`：训练阶段释放 vLLM 占用的显存；
   - `--offload_optimizer true --offload_model true --gc_collect_after_offload true`：vLLM 推理阶段把训练侧模型/优化器状态卸载到 CPU；
   - 降低 `--vllm_gpu_memory_utilization`；
   - 使用 `--vllm_tensor_parallel_size` 做张量并行分摊显存；
   - 在 ZeRO-3 下同步权重到 vLLM 时，用 `--move_model_batches` 分批收集权重，避免一次性 all-gather 全量参数导致显存尖峰。
2. **ZeRO-3 + offload 存在已知的"显存不降反增"或"offload 不生效"问题**：部分版本组合下，开启 `offload_model` 后 actor/ref 模型的显存并未真正释放，进而导致后续 vLLM 初始化因显存不足而失败；排查时应实测 offload 前后的显存快照，而不是仅凭配置项"应该生效"就默认它生效了。
3. **参考模型（ref model）的显存开销容易被低估**：全参数 + `beta>0` 时需要额外加载一份参考模型，这份参考模型同样需要走 ZeRO-3 的 `prepare_deepspeed`，如果它没有被正确 offload，会额外占用与 actor 模型相当的显存，是全参数场景 OOM 排查时最容易被忽略的一环。
4. **收敛速度与稳定性**：全参数训练的有效学习率、梯度裁剪阈值通常需要比 LoRA 更保守（社区实践中全参数 GRPO 的 `learning_rate` 常见设置在 1e-6～5e-7 量级，明显低于 LoRA 场景常见的 1e-5～1e-4），若直接照搬 LoRA 的学习率配置到全参数场景，容易出现训练不稳定甚至指标震荡。

**Full 场景专属排查清单**：
- [ ] 已核对训练侧（actor + ref model + optimizer states）与 vLLM 推理侧的显存分配是否冲突，优先用 `sleep_level`/`offload_*` 组合而非一开始就上多机
- [ ] ZeRO-3 offload 后已实测显存确实释放（打印 `nvidia-smi`/日志中的显存统计，而非只看配置是否写上）
- [ ] `beta>0` 时确认参考模型的显存开销已被纳入预算，且同样正确 offload
- [ ] 权重同步到 vLLM 时使用了 `--move_model_batches` 等分批策略（尤其是 32B+ 级别模型）
- [ ] 学习率、梯度裁剪等超参已按全参数训练的保守区间设置，而非直接沿用 LoRA 配置

### 2.3 场景三：GRPO + 多机多卡分布式训练

**特点**：在单机场景基础上叠加了跨节点通信、权重跨节点同步、日志分散等新变量，是"训练能跑但指标异常"问题最集中的场景之一。

**与单机场景相比的关键不同点**：

1. **多机场景下只有主节点（rank 0）产生完整日志**，其余节点默认不打印训练指标；如果只看非主节点的日志，很容易误判"没有输出=训练卡住"，应先确认自己看的是主节点日志。
2. **"所有 completion 结果雷同、KL 和 loss 恒为 0"是多机 colocate + ZeRO-3 offload 组合下的典型复现现象**：本质是权重未能正确同步到各节点的 vLLM 推理引擎，rollout 阶段各节点一直用同一份（往往是训练开始前的）权重生成，导致组内乃至跨节点的生成结果高度同质化，reward 与 loss 自然长期无变化。排查时应重点核实：跨节点的权重广播/同步是否有网络超时或被静默吞掉的异常。
3. **多机下 vLLM 部署形态的选择直接影响排查思路**：
   - 若采用多机 **server 模式**（如若干节点跑 `swift rollout` 独立部署 vLLM 服务，其余节点跑 `swift rlhf` 通过 HTTP 访问），需要重点核查节点间网络连通性（host/port 配置、防火墙、代理环境变量 `http_proxy`/`https_proxy` 是否被 unset，社区案例中常见因为残留代理环境变量导致节点间 HTTP 请求不通）。
   - 若采用多机 **colocate 模式**，则每个节点各自维护一份 vLLM 实例，权重同步走的是节点内通信 + 跨节点参数广播，ZeRO-3 场景下更容易触发 all-gather/broadcast 的超时或死锁，第一步卡住不动往往是这一类问题，可通过 `py-spy dump` 等工具查看卡住时的调用栈定位是卡在通信原语的哪一步。
4. **`NNODES`/`NODE_RANK`/`MASTER_ADDR`/`MASTER_PORT` 环境变量配置错误**是多机训练"看似启动了但实际各节点未正确组网"的常见原因，尤其是 `MASTER_ADDR` 在容器化/K8s 环境下的解析问题。
5. **ZeRO-3 多机训练速度显著下降**是官方 FAQ 中明确提示需要单独排查的问题类型，与本报告的"指标为 0"问题不同，但常常伴随出现（速度慢+指标异常同时发生时，优先排查是否为同一个权重同步/通信瓶颈导致）。

**多机场景专属排查清单**：
- [ ] 确认查看的是主节点（rank 0）日志，而非误判非主节点"无输出"为异常
- [ ] 若用 server 模式，确认节点间网络连通、代理环境变量已按需 unset、host/port 配置正确
- [ ] 若用 colocate 模式且卡在某一步不动，用 `py-spy dump` 等工具抓取调用栈，定位卡在具体的通信原语（all-gather/broadcast/all-reduce）
- [ ] 对比训练若干步前后，各节点 vLLM 生成内容是否确实发生变化，验证权重同步是否生效
- [ ] `NNODES`/`NODE_RANK`/`MASTER_ADDR`/`MASTER_PORT` 等分布式环境变量在各节点上取值正确且互相一致

### 2.4 场景四：GRPO + vLLM colocate 模式 与 server 模式的选择与排查差异

这一维度会与前述"单机/多机""LoRA/Full"交叉出现，但由于其排查思路差异足够大，单独展开说明。

**核心区别**：
- **Colocate（内置）模式**：训练与推理共享 GPU 资源，vLLM 实例在 Trainer 进程内启动。优点是部署简单、不需要额外硬件；缺点是训练与生成无法真正并行、GPU 在两种负载间来回切换，OOM 频发，且实践上更适合较小规模模型或显存充裕的场景。
- **Server（独立部署）模式**：vLLM 作为独立进程部署在专用 GPU 上，训练进程通过 HTTP 与之通信（`swift rollout` + `swift rlhf --vllm_mode server`）。优点是训练与推理资源隔离、性能更稳定、更易于横向扩展；缺点是需要额外的硬件资源与网络配置，且引入了"训练侧权重如何同步到独立进程的 vLLM"这一额外环节。

**排查侧重点不同**：
- Colocate 模式排查重点在**显存竞争与阶段切换**（`sleep_level`、`offload_*`、`vllm_gpu_memory_utilization`、ZeRO-3 权重收集批次 `move_model_batches`）。
- Server 模式排查重点在**网络与跨进程权重同步**（host/port 是否可达、`vllm_server_timeout` 是否过短、权重同步接口是否报错但被上层吞掉、独立部署的 vLLM 服务本身是否加载了正确版本的模型）。
- 两种模式共同的排查点：**权重是否真的更新到了推理引擎**——最直接的验证方法是在训练若干步前后分别打印/记录 vLLM 生成的样例文本，观察内容是否随训练变化；如果长期不变，无论哪种模式，都应该优先怀疑权重同步环节，而不是 reward 函数或 loss 计算逻辑。

**该维度专属排查清单**：
- [ ] 明确当前使用的是 colocate 还是 server 模式，按上表分别定位排查方向，不要混用两种模式的排查思路
- [ ] Colocate：显存优化项（`sleep_level`/`offload_*`/`vllm_gpu_memory_utilization`/`move_model_batches`）已按官方建议配置
- [ ] Server：网络连通性、超时时间、独立部署的模型版本与训练脚本模型一致
- [ ] 已用"训练前后生成内容对比"的方法验证权重同步确实生效

### 2.5 场景五：GRPO + 多模态（VL）模型

**特点**：在纯文本 GRPO 的基础上叠加了图像/视频输入处理、ViT/aligner 参数是否参与训练等新变量，reward 函数也往往需要同时处理文本与多模态输入的对齐。

**与纯文本场景相比的关键不同点**：

1. **数据对齐问题被放大**：多模态 reward 函数通常需要同时接收 `completions`、文本 `solution`/`answer`，有时还需要图像/视频相关的 kwargs；相比纯文本场景，字段更多、更容易出现"某个字段没有按 `num_generations` 正确展开"从而触发异常兜底、返回全零奖励的情况（这是多模态场景中"reward 恒为 0"复现频率最高的一类根因）。
2. **`freeze_vit` 配置直接影响 LoRA 权重同步策略**：如前所述，若同时对 ViT 层做 LoRA（`freeze_vit false`），"仅同步 LoRA adapter" 的加速优化路径不适用，必须相应在 vLLM 侧开启视觉塔/连接层的 LoRA 支持，否则会出现视觉部分权重未同步、生成内容基于旧视觉编码器产生的问题。
3. **图像/视频预处理参数（如 `MAX_PIXELS`）会显著影响显存与生成稳定性**：多模态场景下像素上限设置不当，容易在多机/大批量下引发 OOM 或生成异常，这类参数在纯文本场景中不存在，需要单独纳入显存预算的考量。
4. **多模态模型的 chat template 更复杂**（涉及图像/视频占位符、多轮工具调用模板等），一旦 SFT 阶段与 GRPO 阶段模板不一致，或没有正确设置 `agent_template`（涉及多轮/工具调用场景），容易导致生成内容格式与 reward 解析逻辑不匹配。
5. **多机多卡多模态 GRPO 更容易在第一步就卡住**：由于视觉编码器的参数量和数据传输量都显著增加，跨节点通信压力更大，官方社区中"多机多卡第一步卡住无响应"的复现案例中多模态大模型（如 Qwen3-VL-32B）占比明显偏高，建议优先用小规模（少量数据、更小分辨率）复现问题，而不是直接在全量多机环境上排查。

**多模态场景专属排查清单**：
- [ ] reward 函数已针对多模态输入（图像/视频相关字段）做过独立单测，覆盖"字段缺失/维度不匹配"等边界情况
- [ ] 若 `freeze_vit false`，已确认使用了完整权重同步而非"仅 LoRA"优化路径，或已在 vLLM 侧正确开启 tower/connector 的 LoRA 支持
- [ ] `MAX_PIXELS`/分辨率相关参数已结合显存预算合理设置
- [ ] SFT 与 GRPO 阶段使用的 chat template / `agent_template` 一致
- [ ] 多机场景已先用小规模数据复现验证，再扩展到全量训练

### 2.6 场景六：GRPO + Megatron-swift（大规模并行训练）

**特点**：面向超大规模模型/集群，引入了 TP/PP/SP/CP/ETP/EP/VPP 等并行策略，是官方框架中并行维度最复杂的训练路径，通常用于全参数或 LoRA 的大规模 MoE/稠密模型训练。

**与常规（Transformers-based）GRPO 相比的关键不同点**：

1. **速度与吞吐问题往往先于指标异常出现**：社区反馈中，Megatron-swift 做 GRPO 训练时若未正确安装依赖的高性能算子库（如 flash-linear-attention、causal-conv1d 等），即使配置正确，训练速度也会显著慢于同等规模的 SFT 训练，这类问题需要先通过 profiling 确认瓶颈在计算还是通信，而不是直接怀疑 GRPO 算法实现有问题。
2. **权重导出与 vLLM 同步路径不同**：Megatron 格式权重需要先导出为 HF 格式才能供 vLLM 更新使用，官方建议将导出的 HF 格式权重存放于 CPU 主存以降低 GPU 显存占用，这是 Transformers-based 场景不存在的额外环节，一旦这一步配置不当，同样会导致"vLLM 一直使用旧权重生成"的经典故障模式。
3. **并行策略组合（TP/PP/SP/CP/ETP/EP/VPP）与 GRPO 的 rollout/reward 阶段的交互更复杂**：例如流水线并行（PP）下，不同 stage 的模型分片如何汇总生成结果、专家并行（EP）下 MoE 路由与 reward 计算的对齐，都是常规单卡/数据并行场景不需要考虑的维度，出现指标异常时应优先怀疑并行切分是否正确，再考虑奖励函数本身。
4. **官方最佳实践仍在持续完善**：截至目前，Megatron-swift 上 GRPO 的完整最佳实践文档相对 Transformers-based 路径更少，遇到问题时应更依赖官方 issue 区的最新讨论和版本更新记录，而非假设所有 Transformers-based 场景的经验能直接平移。

**Megatron-swift 场景专属排查清单**：
- [ ] 高性能算子依赖（如 flash-linear-attention、causal-conv1d 等）已按模型架构要求正确安装
- [ ] 权重导出（Megatron → HF）与 vLLM 同步路径已验证生效，导出权重存放位置符合显存预算
- [ ] 并行策略组合（TP/PP/SP/CP/ETP/EP/VPP）与模型结构、集群拓扑相匹配，必要时先用较简单的并行组合复现问题
- [ ] 已核对当前 ms-swift 版本在 Megatron + GRPO 组合下是否有已知限制或 workaround

## 第三部分：完整案例复盘（以 ms-swift 4.4.0 + Qwen3-32B + GRPO + LoRA，loss 和 reward 同时恒为 0 为例）

本案例对应本报告"2.1 GRPO + LoRA 场景"，且属于单机场景（若为多机，需要额外并入"2.3 多机场景"的排查项）。完整流程如下：

**Step 1：缩小复现规模**
将 `num_generations` 调小（如 4）、`per_device_train_batch_size=1`、`logging_steps=1`，只用极少量数据（如 20 条），开启 `--log_completions true`，用最低成本稳定复现问题。

**Step 2：检查真实生成内容（对应 L2 采样层）**
查看生成文本是否为空、是否高度重复退化、是否携带 `<think>...</think>` 等 Qwen3 特有标签而奖励函数未适配。若生成内容本身已异常，定位到 L2：检查模型是否为 instruct 版本、chat template/`--system` 提示词、采样温度等。

**Step 3：若生成正常但 reward=0，定位到奖励函数（对应 L3）**
剥离 reward 函数单独测试，重点核查字段名是否对齐、ground truth 与 `num_generations` 份 completion 的展开对齐逻辑是否正确（这是历史复现最多的根因）、正则解析是否兼容 Qwen3 输出格式。

**Step 4：核对数据集字段与预处理结果（对应 L1）**
脱离训练脚本单独加载并打印数据集前几条，确认预处理后喂给 reward 函数的字段确实存在且内容合理。

**Step 5：核实 LoRA + vLLM 权重同步问题（对应 L2 深层 / 2.1 节 LoRA 特有排查项）**
确认 `vllm_enable_lora`（若开启）与 `vllm_max_lora_rank` 与训练脚本 `lora_rank` 一致；对比训练若干步前后生成内容是否变化，验证权重同步是否生效。

**Step 6：核对版本兼容性（对应 L0）**
确认 ms-swift 4.4.0 配套的 transformers/trl/vllm/deepspeed 版本是否为官方推荐组合，按"版本号+现象关键词"搜索 GitHub issue 确认是否有已知问题及修复记录。

**Step 7：结论与修复对照表**

| 定位结论 | 修复动作 |
|---|---|
| 数据字段与 reward 函数 kwargs 不匹配 | 统一字段命名，reward 函数入口打印实际 kwargs keys 后修正 |
| ground truth 与 completions 未按 num_generations 正确展开对齐 | 修复对齐逻辑，加入长度断言而非静默返回全 0 |
| 生成内容退化/重复 | 检查模型版本、chat template、system prompt，必要时先做 SFT 再接 GRPO |
| reward 函数未适配 Qwen3 思考标签输出格式 | 先剥离 `<think>` 段落再提取最终答案 |
| LoRA 权重未同步到 vLLM | 检查 `vllm_enable_lora`/`vllm_max_lora_rank` 一致性，确认同步日志无异常 |
| 组内 reward 方差为 0（`frac_reward_zero_std` 接近 1） | 提高采样温度、增大 num_generations、检查数据难度分布 |
| 版本兼容性 bug | 升级/降级到官方验证过的版本组合，或应用社区给出的临时 workaround |

**Step 8：验证修复效果**
在最小复现场景中确认 `reward` 有波动、`reward_std>0`、`loss` 非恒 0、`grad_norm>0` 后，再恢复到完整规模训练，并持续监控 `frac_reward_zero_std`、`kl`、`clip_ratio/*`，避免中途再次出现信号坍缩。

## 第四部分：跨场景通用预防清单

在正式启动任意场景的 GRPO 训练前，建议逐项确认（场景特有项见第二部分对应小节）：

- [ ] 已用最小数据/最小 batch 跑通一轮，并人工核查过 `log_completions` 输出内容
- [ ] reward 函数已脱离训练框架做过独立单测，覆盖"正确/错误/无法解析/字段缺失"等情况
- [ ] 数据集字段名与 reward 函数期望的 kwargs key 完全一致，ground truth 与 completions 的对齐逻辑有显式长度校验
- [ ] 确认模型为对齐过的 instruct 版本，chat template / system prompt 配置正确
- [ ] 已明确当前训练形态（LoRA/Full）、部署形态（单机/多机、colocate/server）、模型形态（纯文本/多模态）、并行框架（Transformers-based/Megatron），并对照第二部分找到对应场景的专属排查项
- [ ] 已核对 ms-swift / transformers / trl / vllm / deepspeed 的版本组合是否为官方推荐
- [ ] 已了解各监控指标含义（尤其 `reward_std`、`frac_reward_zero_std`、`kl`、`grad_norm`），避免将预期行为（如 `beta=0` 导致 `kl=0`）误判为 bug
- [ ] 已用"训练前后生成内容对比"方法验证权重同步（LoRA/Full、colocate/server、单机/多机场景通用）
- [ ] 训练过程中持续监控上述指标，而非仅盯 `loss`/`reward` 两个顶层数字
