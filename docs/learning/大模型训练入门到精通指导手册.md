## 一、这本手册解决什么问题

大模型（LLM/多模态大模型）训练领域，对于两类人群存在明显的"认知断层"：

1. **传统小模型训练背景的人**：熟悉训练循环、反向传播、优化器、正则化、交叉验证这些"训练的基本功"，但对"为什么大模型训练需要分布式、什么是 3D 并行、为什么 SFT/RLHF 是必需的独立阶段、什么是涌现能力、scaling law 是什么"这些大模型时代特有的概念缺乏系统认知。他们的迁移难点主要在于**规模与工程复杂度带来的范式转变**——很多在小模型上"理所当然"的做法（比如整个数据集读进内存、单卡调参跑几十个 epoch）在大模型场景下完全不成立。

2. **大模型推理/应用背景的人**：非常熟悉"模型是一个黑箱服务"这件事——知道怎么部署、怎么写 Prompt、怎么调 OpenAI 兼容 API，甚至知道 KV Cache、量化这些推理侧概念，但对"这个模型是怎么被训练出来的"完全没有一手经验。他们的迁移难点在于**从"消费模型"到"生产模型"的视角转变**——需要理解数据从哪来、loss 是怎么算的、为什么会有 base/chat/reasoning 模型的区分、SFT 和 RLHF 到底在训练什么。

本手册的定位，就是**搭建一座连接这两类背景与"能够独立开展大模型训练相关研究工作"之间的桥梁**：不要求你从本手册直接学会敲代码调库（那是具体框架文档/随附的 ms-swift 分析文档该做的事），而是要求你读完之后，具备完整、系统、结构化的知识地图与心智模型，知道：

- 大模型训练全流程有哪些阶段，每个阶段解决什么问题；
- 每个阶段涉及的核心技术概念是什么、为什么需要它、它的大致原理（用伪代码/图示表达思想，而非代码实现）；
- 每个方向应该进一步阅读哪些论文、课程、开源项目去深入；
- 面对一个具体的大模型训练任务，应该如何规划技术路线、评估资源需求、避开常见的坑。

# 第 01 章　大模型训练全景与心智转变

## 1.1 先给出一张全局地图

在深入任何细节之前，先建立一张"大模型是怎么被生产出来的"全景图。一个现代大语言模型从无到有、再到能被用户使用，大致经过下面这条流水线：

```
海量原始文本/多模态数据
        │  收集、清洗、去重、配比
        ▼
   预训练数据集（Trillions tokens 级别）
        │
        ▼
┌───────────────────────────┐
│  预训练 (Pretraining/PT)   │  ← 自监督学习，学"语言/世界知识"
│  产出：Base Model          │
└─────────────┬─────────────┘
              │ 少量高质量指令数据
              ▼
┌───────────────────────────┐
│  有监督微调 (SFT)           │  ← 学"听懂指令、按格式回答"
│  产出：Chat/Instruct Model  │
└─────────────┬─────────────┘
              │ 偏好数据/规则化奖励
              ▼
┌───────────────────────────┐
│  对齐训练 (RLHF/DPO/GRPO)   │  ← 学"人类更喜欢哪种回答/怎样推理更好"
│  产出：Aligned/Reasoning Model│
└─────────────┬─────────────┘
              │
              ▼
        评测、量化、部署
              │
              ▼
        用户看到的最终产品
```

这条流水线里，**预训练**是最烧钱、最考验工程能力的一环（往往需要成百上千张 GPU 跑数周甚至数月），**SFT** 相对轻量（很多场景下单机多卡甚至单卡 + PEFT 就能完成），**对齐训练**居中，且是近两年（尤其是"推理模型"兴起后）技术演进最活跃的部分。

对绝大多数从传统小模型或推理背景转型的人来说，**日常工作接触最多的是 SFT 与对齐训练这两个阶段**（做预训练需要的资源门槛通常只有头部机构才具备），因此本手册虽然会覆盖预训练原理（第 5 章），但会把更多篇幅放在数据工程、SFT/PEFT、RLHF 体系上——这与随附的 ms-swift 文档的实际功能重心（该框架同样以 SFT/PEFT/RLHF 为主，预训练能力更多通过 Megatron-SWIFT 子系统覆盖）是吻合的。

## 1.2 如果你来自传统小模型训练背景

### 1.2.1 熟悉的东西还有用吗？

你过去掌握的这些概念，**在大模型时代依然完全有效，是地基而非过时知识**：

- 反向传播、梯度下降、Adam/AdamW 优化器；
- 过拟合/欠拟合、正则化、学习率调度（warmup、cosine decay）；
- 训练/验证/测试集划分的思想（虽然大模型时代"验证集"的用法发生了变化，见下）；
- Batch Size、梯度累积的基本原理；
- 混合精度训练（AMP/FP16/BF16）。

### 1.2.2 需要重新建立的认知：从"炼小模型"到"炼大模型"的五个范式转变

**转变一：从"整个数据集能放进内存/单机磁盘"到"数据集本身就需要分布式存储与流式读取"。** 预训练数据集常以 TB 甚至 PB 计，不可能一次性加载；训练框架普遍采用 Streaming Dataset（边读边训，不做全量预处理落盘）或预先 Tokenize 后以分片二进制格式存储（如 Megatron 使用的 `.bin`/`.idx` 格式），Dataloader 需要考虑跨机分片、断点续训时如何恢复到准确的数据读取位置。

**转变二：从"单卡/单机多卡就能跑完"到"必须理解分布式并行策略"。** 传统小模型很少需要关心"模型参数本身放不下一张卡"这种问题；大模型（尤其是 7B 以上）预训练与全参数微调基本必须使用数据并行（DP）+ 张量并行（TP）+ 流水线并行（PP）等组合策略。这是本手册第 6 章的重点，也是大模型训练区别于传统训练"工程复杂度"最核心的来源。

**转变三：从"追求单一 loss/指标最优"到"训练目标本身是分阶段、分性质的"。** 传统监督学习通常是"一个任务、一个 loss、一个评价指标"；大模型训练把"学知识"（预训练）、"学格式与指令遵循"（SFT）、"学偏好/对齐"（RLHF）拆成了性质完全不同的独立阶段，每个阶段的数据分布、loss 形式、评价方式都不同。理解"当前是哪个阶段、这个阶段到底想让模型学到什么"，是排查很多训练问题（如"为什么 SFT 之后模型变笨了"）的关键出发点。

**转变四：从"验证集判断是否过拟合"到"用标准化评测榜单 + 人工/模型评判判断能力"。** 大模型很少用传统意义的"验证集 loss 是否上升"来判断训练是否该早停——更常见的做法是定期在标准评测集（MMLU、C-Eval、GSM8K、HumanEval 等，见第 10 章）上跑分，以及用人工评估或"用更强模型当裁判"（LLM-as-a-Judge）的方式评价生成质量。

**转变五：从"炼出模型即终点"到"训练与推理形成双向反馈"。** 大模型时代，很多训练方法（尤其是 RLHF/GRPO）本身就需要在训练循环中调用推理引擎做 Rollout（采样生成），训练与推理的边界比传统监督学习模糊得多——这也是为什么第 12 章要专门讲"推理侧知识如何反哺训练侧理解"。

## 1.3 如果你来自大模型推理/应用背景

### 1.3.1 你已经具备的优势

- 你知道模型的输入输出形态（Prompt → 生成文本/Token 序列），理解 Chat Template、System Prompt 这些概念；
- 你可能已经了解 KV Cache、量化（INT8/INT4/GPTQ/AWQ）、批处理调度（Continuous Batching）等推理优化技术，这些知识在理解"训练产出的模型如何被高效使用"、以及"RLHF 训练中的 Rollout 环节为什么要用推理引擎加速"时非常有用（第 12 章会详细展开这层关联）；
- 你可能已经用过 LangChain/Agent 框架、了解工具调用（Function Calling）的数据格式，这对理解 SFT 阶段的 Agent Template（随附 ms-swift 文档第 4 章有专门介绍）会有天然的亲和度。

### 1.3.2 需要补齐的认知

**认知一：模型不是一个黑箱"能力常数"，而是数据与训练目标共同塑造的产物。** 推理视角容易把模型看成"一个固定的、给定输入必然产生某种输出分布的函数"；训练视角需要建立"模型的每一种能力/每一种行为倾向，都对应着训练数据中某种分布或某个训练阶段的某种目标函数"这样的因果链条认知。例如模型"啰嗦"，往深挖可能对应 SFT 数据里回复普遍偏长，或者奖励模型偏好长回复导致的 Reward Hacking（第 8 章）。

**认知二：Loss 曲线、梯度范数这些"训练内部信号"需要重新学习解读。** 推理侧几乎不接触这些信号，但它们是判断"训练是否健康"最直接的证据（第 10 章）。

**认知三：理解"参数高效微调"与"全参数微调"的资源与效果权衡。** 推理侧接触到的往往是"别人训好的模型"，不需要关心训练资源；转向训练侧后，"用多大资源、多长时间、能达到什么效果"是每天都要做的权衡决策（第 6、7 章）。

## 1.4 两类背景共同需要建立的核心心智模型：Scaling Law 与"涌现"

无论来自哪种背景，理解大模型训练都绕不开两个奠基性认知：

**Scaling Law（缩放定律）**：模型性能（通常用 loss 衡量）与模型参数量、训练数据量、计算量三者之间存在可预测的幂律关系。这一发现（最早由 OpenAI 的 Kaplan 等人系统提出，后经 DeepMind 的 Chinchilla 论文修正了"给定计算预算下参数量与数据量的最优配比"）是大模型训练一切资源规划决策的理论基础——它告诉工程师"投入更多计算大概率能换来可预测的性能提升"，这也是大模型研究与传统小模型研究在方法论气质上最大的差异之一：传统小模型研究更依赖架构创新与特征工程，大模型研究阶段性地更依赖"在正确的架构框架下把 Scale 做对"。

**涌现能力（Emergent Abilities）**：某些能力（如多步推理、上下文学习 In-Context Learning）只有当模型规模跨过某个临界点后才会突然出现，而不是随规模平滑增长——这一现象本身在学术界仍有争议（部分研究认为"涌现"很大程度是评价指标的非线性/离散化造成的测量假象，而非能力本身的突变），但它提醒工程师：**用小模型做的实验结论，不一定能线性外推到大模型上**，这是做技术选型和消融实验（Ablation Study）时必须保持的警惕。

## 2.1 Transformer 架构速览

当前几乎所有主流大模型都基于 Transformer Decoder-only 架构（GPT 系列、LLaMA、Qwen、DeepSeek 等）。核心组件：

```
输入 Token 序列
      │  Embedding 查表
      ▼
  词向量序列 + 位置编码信息
      │
      ▼
┌─────────────────────────┐
│   N 层 Transformer Block │  重复 N 次（N 通常几十层）
│  ┌─────────────────────┐ │
│  │ 自注意力 (Self-Attn) │ │  ← 让每个位置"看到"前面所有位置的信息
│  └─────────┬───────────┘ │
│  ┌─────────▼───────────┐ │
│  │ 前馈网络 (FFN/MLP)    │ │  ← 对每个位置独立做非线性变换，参数量主要集中在此
│  └──────────────────────┘ │
│  （每个子模块前后配合 残差连接 + 归一化）│
└─────────────┬─────────────┘
              ▼
        输出层 (LM Head)
              │  与词表大小相同维度的 logits
              ▼
        Softmax → 下一个 Token 的概率分布
```

**自注意力机制的核心思想（伪代码，非真实实现）**：

```
function self_attention(X):
    Q = X @ W_q     # 每个位置生成一个"查询"
    K = X @ W_k     # 每个位置生成一个"键"
    V = X @ W_v     # 每个位置生成一个"值"
    scores = Q @ K.T / sqrt(d_k)     # 计算任意两个位置的相关性
    scores = apply_causal_mask(scores)  # 只允许看"之前"的位置（decoder-only 的关键）
    weights = softmax(scores)
    output = weights @ V
    return output
```

其中 `apply_causal_mask` 是 Decoder-only 架构"只能看过去、不能看未来"这一根本约束的实现方式，这也是为什么这类模型天然适合"自回归生成"（一个个 Token 往后预测）。

**多头注意力（Multi-Head Attention）**：把上述过程在多个"子空间"里并行做多次（多个头），再拼接结果——直觉上是让模型能同时从多个不同角度捕捉 Token 之间的关系。近年的重要变体包括 **GQA（Grouped-Query Attention，多个 Query 头共享同一组 Key/Value 头，用于降低推理时 KV Cache 显存占用）** 与 **MQA（Multi-Query Attention，所有 Query 头共享一组 KV，GQA 是 MQA 与传统 MHA 之间的折中）**——这两个概念对理解现代模型的推理效率优化以及训练时的显存占用都很关键。

## 2.2 现代架构的几个关键改进点

相比最早的 Transformer/GPT-2 架构，现代大模型（LLaMA 系为代表）普遍采用以下改进，理解它们"解决了什么问题"即可，不需要记住公式：

| 改进项 | 替代的旧方案 | 解决的问题 |
|---|---|---|
| RMSNorm | LayerNorm | 计算更简单（去掉了减均值的步骤），训练更稳定、速度更快 |
| RoPE（旋转位置编码） | 绝对位置编码/可学习位置编码 | 更好的长度外推性（训练时见过的序列长度之外，推理时依然有较好表现），且是"相对位置"编码，更符合语言的相对位置直觉 |
| SwiGLU（激活函数） | ReLU/GeLU | 在相同参数量下通常带来更好的效果（代价是 FFN 层需要多一组权重矩阵） |
| Pre-Norm 结构 | Post-Norm 结构 | 归一化放在子模块之前而非之后，显著提升深层网络的训练稳定性，是训练大模型不容易发散的重要工程经验 |

**多模态场景下的位置编码扩展**：M-RoPE（Multi-modal RoPE，如 Qwen-VL 系列采用）需要同时编码时间、宽、高等多个维度的位置信息，这是第 11 章多模态训练会涉及的概念，此处先建立"位置编码在多模态场景需要额外设计"这一认知即可。

## 2.3 训练目标：语言模型在学什么

预训练阶段的核心训练目标是**自回归语言建模（Causal/Autoregressive Language Modeling）**：给定前面的 Token，预测下一个 Token 是什么，用**交叉熵损失（Cross-Entropy Loss）**衡量预测分布与真实下一个 Token 之间的差距。

```
对序列 [t1, t2, t3, ..., tn]：
loss = sum over i of  CrossEntropy( model_predict(t1...t_{i-1}), 实际的 t_i )
```

**困惑度（Perplexity, PPL）** 是交叉熵 loss 的指数形式，是预训练阶段最常用的"模型好坏"直观指标之一，PPL 越低说明模型对数据的预测越"不意外"，即语言建模能力越强。但需要注意：**PPL 低不直接等价于"下游任务能力强"或"回答质量好"**，这是很多从预训练视角转向下游能力评估的人容易踩的认知误区，也是第 10 章要专门强调"评测体系需要多元化"的原因。

SFT 阶段的训练目标形式上依然是交叉熵，但有一个关键区别——**Loss Masking（损失遮罩）**：只对"模型应该学会生成"的部分（通常是助手的回复内容）计算 loss，用户输入的部分（Prompt/Instruction）不参与 loss 计算，即被"mask"掉。这是理解 SFT 与预训练在实现层面最直接的区别：

```
样本: [System Prompt][User: "介绍一下你自己"][Assistant: "我是..."]
loss_mask:     0            0                        1  (仅这部分token参与loss计算)
```

## 2.4 优化器与训练稳定性

大模型训练几乎清一色使用 **AdamW** 优化器（Adam 的权重衰减修正版本），核心原因是它对稀疏梯度、不同参数量级的自适应能力，在大规模、深层网络上表现稳健。需要额外理解的稳定性相关概念：

- **学习率预热（Warmup）+ 余弦衰减（Cosine Decay）**：训练初期用很小的学习率线性爬升一段步数，再按余弦曲线逐渐衰减到接近 0——这是大模型训练几乎标配的学习率调度策略，直觉上是"训练初期模型参数还很随机，大学习率容易导致训练不稳定甚至发散，需要先小心翼翼地'热身'"；
- **梯度裁剪（Gradient Clipping）**：限制梯度的最大范数，防止某个 batch 出现异常大梯度导致参数更新过猛（俗称"Loss Spike"，第 10 章会讲怎么在监控中发现和处理它）；
- **混合精度训练（Mixed Precision）**：用 FP16 或 BF16（而非传统的 FP32）做大部分计算以节省显存和加速计算，同时保留部分关键计算（如梯度累加、Loss Scaling）用更高精度进行以避免数值溢出/下溢。**BF16 相比 FP16 数值范围更大（与 FP32 相同的指数位宽度），在大模型训练中更不容易出现数值溢出问题，是目前的主流选择**，这一点对排查"为什么用 FP16 训练总是出现 NaN"的问题很关键。

## 2.5 Scaling Law 与计算预算规划：一个基础但重要的量化直觉

Chinchilla 论文给出的核心结论是：在给定计算预算（FLOPs）下，模型参数量与训练 Token 数量应该按大致相等的比例增长才能达到最优效果，经验法则常简化表述为**训练 Token 数量应当是模型参数量的约 20 倍左右**（这一比例在近年"小模型 + 超大数据量"路线兴起后，实践中已经被大幅突破，很多现代模型的训练 Token 数远超这一比例，说明该经验法则并非绝对真理，而是特定计算预算与数据可得性假设下的产物，理解其"存在但会被后续研究修正"这一性质比记住具体数字更重要）。

对于从事微调/对齐工作（而非从零预训练）的读者，这一定律的实践意义更多体现在**理解"为什么大厂敢用某个参数规模的模型去处理某类任务"背后的资源逻辑**，以及在做全参数微调的资源预算评估时，可以类比参考"参数量-数据量-计算量"三者的关联直觉。

# 第 03 章　数据工程

业界有一句被反复引用的经验总结："大模型训练，数据决定上限，算法和工程决定能否接近这个上限。"本章系统梳理预训练数据与 SFT/对齐数据这两大类数据在工程上的处理方式。

## 3.1 预训练数据工程全景流程

```
原始数据源                              
（网页爬取 Common Crawl、书籍、代码仓库、           
 学术论文、百科、社交媒体、多语言语料...）           
        │
        ▼
┌───────────────────┐
│ 1. 数据抽取与清洗    │  去 HTML 标签、去乱码、语言识别过滤、
│                    │  去除广告/导航栏等噪声文本
└─────────┬──────────┘
          ▼
┌───────────────────┐
│ 2. 质量过滤          │  基于规则（长度、符号占比、重复行）+
│                    │  基于模型（用小分类器打分，过滤低质量文本）
└─────────┬──────────┘
          ▼
┌───────────────────┐
│ 3. 去重 (Dedup)      │  文档级/段落级 去重，常用 MinHash/SimHash
│                    │  近似去重算法（精确去重成本过高）
└─────────┬──────────┘
          ▼
┌───────────────────┐
│ 4. 数据配比 (Mixing)  │  决定网页/代码/书籍/多语言等各来源的采样比例
│                    │  （直接影响模型的知识结构与能力偏向）
└─────────┬──────────┘
          ▼
┌───────────────────┐
│ 5. 安全与合规过滤     │  过滤隐私信息(PII)、有害内容、版权敏感内容
└─────────┬──────────┘
          ▼
┌───────────────────┐
│ 6. Tokenize 落盘     │  转换为 Token ID 序列，打包为训练框架可直接
│                    │  流式读取的二进制格式（见第 4 章 Tokenizer）
└────────────────────┘
```

### 3.1.1 去重为什么如此重要

预训练语料中的重复内容（尤其是网页爬取数据中大量的转载、镜像站、模板化文本）如果不去重，会导致：模型在这些重复片段上"过拟合"式地记忆（增加隐私泄露、生成训练数据原文的风险）；有效信息密度下降，浪费宝贵的计算预算。业界主流方案是**近似去重**而非逐字节精确比对——因为语料规模巨大，精确的全量两两比较在计算上不可行。核心思路（伪代码化）：

```
function minhash_dedup(documents):
    for doc in documents:
        shingles = extract_ngram_shingles(doc)      # 提取文档的 n-gram 特征集合
        signature = compute_minhash_signature(shingles)  # 压缩成固定长度的"指纹"
        bucket = locality_sensitive_hash(signature)   # LSH 分桶，相似文档大概率落入同一桶
    for bucket in buckets:
        candidates = documents_in(bucket)
        for pair in candidate_pairs(candidates):
            if estimated_similarity(pair) > threshold:
                mark_as_duplicate(pair)
```

这套"MinHash + LSH（局部敏感哈希）"的组合，是处理 TB 级文本去重的标准工程范式，值得深入理解其原理（而非仅停留在"知道有这么个技术"的层面），因为它在数据工程面试与实际工作中都是高频考点。

### 3.1.2 数据配比：一个"炼丹"色彩浓厚但影响巨大的决策

不同来源数据的采样比例（比如网页文本 : 代码 : 书籍 : 学术论文 : 多语言语料 的比例），会直接决定模型的能力"性格"——代码数据比例高的模型，逻辑推理与结构化输出能力通常更强（这也是为什么很多研究发现"混入适量代码数据能提升模型的通用推理能力"，即便下游任务并非代码任务）；多语言比例决定模型的多语言能力上限；书籍与学术语料通常被认为是"高质量、长程依赖丰富"的数据，会被有意提高采样权重（即同一份数据可能被采样"读"不止一遍，这被称为**过采样/重复采样**，需要与"去重"这一概念的应用层次区分开——去重针对的是内容重复的不同文档，过采样针对的是刻意提高高质量数据的出现频次）。

### 3.1.3 数据污染检测（Contamination Check）

一个容易被忽视但非常重要的工程环节：如何确保预训练/微调数据中，没有意外混入将要用于评测的测试集内容（这会导致评测分数虚高，产生"作弊"效果，损害评测的可信度）。标准做法是对预训练语料与所有会用到的评测基准做 n-gram 重叠度检测，将高度重叠的样本从训练集中剔除。这一步骤在发布任何自研模型的评测结果时，都应作为可信度的必要说明项。

## 3.2 SFT 数据工程

SFT 数据的核心组织形式是**多轮对话格式**（业界事实标准，`messages` 数组，每条包含 `role`（system/user/assistant/tool）与 `content`），随附的 ms-swift 文档第 4 章对该标准格式与 AutoPreprocessor 自动探测机制有详细说明，本手册在此基础上补充"数据从哪里来、怎么构造"这一更上游的问题：

**SFT 数据的三大来源**：
1. **人工标注**：由标注团队根据任务需求编写高质量的指令-回复对，成本最高但质量与可控性也最高，常用于对齐核心场景（如安全对话、复杂推理示范）；
2. **开源数据集**：如 Alpaca、ShareGPT、OpenOrca 等，覆盖面广但质量参差不齐，通常需要二次清洗筛选；
3. **模型合成数据（Synthetic Data）**：用更强的模型（如闭源旗舰模型）生成指令-回复对，再经过质量过滤/去重后使用，是近年成本效益最高、也最主流的数据获取方式之一，代表性方法论包括 **Self-Instruct**（让模型自己生成新指令并回答，迭代扩充数据集）和 **Evol-Instruct**（对已有指令做"复杂化改写"，逐步提升指令难度分布，代表工作是 WizardLM 系列论文）。

**数据质量高于数量**：LIMA 论文（"Less Is More for Alignment"）是这一领域的重要参考——该研究发现，仅用约一千条精心挑选的高质量 SFT 样本，就能让 Base 模型获得相当不错的指令遵循能力，其核心论点是**预训练阶段已经学到了几乎全部所需知识与能力，SFT 阶段的作用更多是"激活/校准"这些能力的表达方式，而非灌输新知识**——这一论点对理解"为什么少量高质量数据往往比海量低质量数据效果更好"提供了理论支撑，也是数据工程中"质量优先于数量"这一实践共识的重要来源。

## 3.3 数据格式与打包：Packing 技术

无论预训练还是 SFT，训练框架都倾向于把多条变长样本"打包（Packing）"进固定长度的训练序列，以消除因样本长度不一致、需要 padding（填充）到最长样本而造成的算力浪费。

```
不做 Packing：
样本A(长度50) → [====填充到512====]   浪费 462 个位置的算力
样本B(长度200)→ [========填充到512====]   浪费 312 个位置的算力

做 Packing：
[样本A(50) | 样本B(200) | 样本C(180) | 样本D(80) | 填充2] → 一条512长度的序列，几乎无浪费
```

Packing 需要额外维护"样本边界"信息，确保注意力机制不会让拼接进同一条序列的不同原始样本之间产生跨样本的注意力"泄漏"（即样本 A 的 Token 不应该注意到样本 B 的内容），这通常通过特殊的注意力 Mask 或者位置编码重置来实现。随附 ms-swift 文档第 17 章提到的"多模态 Packing 可将训练速度提升 100% 以上"，正是这一技术在多模态场景下收益被进一步放大的例证（多模态样本长度差异更大）。

| datasets（HuggingFace） | 通用数据集加载、处理、流式读取库，是几乎所有主流训练框架的数据层基础依赖之一 |

下一章讨论文本如何被转换为模型可处理的数字序列：Tokenizer 与词表。
# 第 04 章　Tokenizer 与词表

## 4.1 为什么 Tokenizer 值得单独一章

Tokenizer（分词器）负责把原始文本切分成一个个"Token"并映射为整数 ID，是文本进入模型前的最后一道、也是最容易被低估的工序。它的设计直接影响：模型能高效处理哪些语言/领域文本（比如词表对中文/代码优化不足，会导致同样内容需要更多 Token 表示，间接推高训练与推理成本、压缩上下文窗口的实际可用长度）；数字、特殊符号的处理方式（会直接影响数学推理、代码生成能力）；多模态与工具调用等特殊 Token 的设计空间。

## 4.2 主流子词切分算法

现代大模型清一色采用"子词（Subword）"级别的切分，而非传统 NLP 常见的"整词"或"字符"级别，核心动机是在"词表大小"与"能否处理未登录词（OOV）"之间取得平衡——常见词切成一个 Token，罕见词/未见过的词切成若干个子词单元拼接表示，理论上不存在真正的 OOV 问题。

| 算法 | 核心思路（简述，非公式） | 代表使用者 |
|---|---|---|
| BPE（字节对编码） | 从字符级别开始，反复把"最高频出现的相邻符号对"合并成一个新符号，直到达到目标词表大小 | GPT 系列、LLaMA 系列 |
| Byte-level BPE | 在原始 BPE 基础上，把切分的最小单元从"Unicode 字符"改为"UTF-8 字节"，彻底避免任何字符编码/未知字符导致的处理失败 | GPT-2 及之后几乎所有主流模型 |
| WordPiece | 与 BPE 思路接近，但合并规则基于"能否提升语言模型似然"而非单纯词频 | BERT 系列 |
| Unigram（SentencePiece 的一种模式） | 反向思路：从一个很大的候选子词集合出发，用概率模型迭代地"剪掉"对整体似然贡献最小的子词，直到收敛到目标大小 | T5、部分多语言模型 |

**BPE 训练过程伪代码（思想示意）**：

```
function train_bpe(corpus, target_vocab_size):
    vocab = set of all individual characters/bytes in corpus
    words = split corpus into space-separated words, each represented as char sequence
    while len(vocab) < target_vocab_size:
        pair_counts = count all adjacent symbol pairs across words
        best_pair = pair with the highest count
        merge best_pair into a new single symbol in all words
        add new symbol to vocab
    return vocab, merge_rules
```

## 4.3 词表大小的工程权衡

词表并非越大越好：

- **词表变大** → 每个 Token 平均携带的语义信息更多，相同文本可以用更少的 Token 表示（有利于压缩上下文长度占用、提升推理吞吐），但 Embedding 层与输出层（LM Head，通常与 Embedding 共享权重）的参数量随词表大小线性增长，对小模型而言这部分参数占比会变得不可忽视；
- **词表变小** → 同样文本需要更多 Token 表示（推高训练/推理成本、挤占有效上下文窗口），但 Embedding 层参数更省。

现代主流模型的词表大小普遍在 3 万到 25 万之间不等（不同模型、不同语言覆盖范围差异很大），近年来伴随"多语言能力"与"更长有效上下文"的需求提升，词表规模呈现总体扩大趋势（例如很多面向中文优化的模型会显著扩充中文子词以降低中文文本的平均 Token 消耗）。

## 4.4 特殊 Token 与 Chat Template

除了从语料中学到的普通子词，Tokenizer 词表中还包含一批**特殊 Token（Special Tokens）**，承担控制信号的作用而非表达自然语言语义，例如：

- 序列起止标记（BOS/EOS，Begin/End Of Sequence）；
- 角色分隔标记（用于在多轮对话格式中标记 system/user/assistant 的边界，是 **Chat Template** 机制的底层依赖）；
- 工具调用相关标记（用于 Agent/Function Calling 场景，标记"这里开始是一次工具调用请求/工具返回结果"）；
- 多模态占位符（如 `<image>`、`<video>`，见第 11 章）；
- 面向"推理模型"新增的思维链分隔标记（如标记"这里开始/结束是模型的内部思考过程，与最终呈现给用户的回答内容做区分"，这是近两年推理模型兴起后新出现的特殊 Token 设计需求）。

**Chat Template** 是把"结构化的多轮对话 messages 列表"渲染成"一段连续文本字符串（再被 Tokenizer 切分成 Token 序列）"的规则集合，不同模型家族的 Chat Template 格式互不相同（这也是为什么同一份 `messages` 格式的数据，喂给不同模型训练/推理时，编码出来的实际 Token 序列完全不同）——这部分内容与随附 ms-swift 文档第 4 章介绍的 Template 编码体系（负责把 messages 编码为 `input_ids`/`labels`/`loss_scale`）是同一层面的概念，具体的编码链路实现建议直接参照该文档。

## 4.5 是否需要训练/扩充自己的 Tokenizer

对绝大多数下游微调场景（SFT/PEFT/RLHF），**直接复用 Base 模型自带的 Tokenizer 是绝对首选**，因为 Tokenizer 与模型的 Embedding 层是绑定训练出来的，更换或扩充词表意味着需要对新增部分的 Embedding 做额外的初始化与训练适配，工程复杂度与风险都显著提高，只有在以下场景才需要考虑：

1. **从零预训练自己的模型**：此时训练一个契合自身领域/语种数据分布的 Tokenizer 是必要步骤；
2. **对某个语种/领域的 Token 效率有极端优化需求**（比如已有 Base 模型对某小语种支持很差，每个字符都要切成多个 Token，希望通过扩充词表大幅降低该语种的 Token 消耗）——这类"词表扩充（Vocabulary Extension）"工作需要谨慎处理新增 Token 的 Embedding 初始化策略（常见做法是用相似已有 Token 的 Embedding 做加权初始化，而非随机初始化），并且通常需要搭配额外的继续预训练（CPT）阶段让模型"学会"新增 Token 的语义，而不能指望仅靠 SFT 阶段的少量数据让新 Token 获得充分训练。

## 4.6 本章小结与学习建议

Tokenizer 是一个"一旦选定就很难更改"的底层基础设施决策，建议的学习重点不在于记住每种算法的数学细节，而在于建立"Token 效率如何影响成本与效果""特殊 Token 与 Chat Template 如何决定训练数据的最终编码形态"这两条因果链条的直觉。

推荐资料：HuggingFace `tokenizers` 库文档与教程（可交互式体验 BPE 训练过程）；SentencePiece 项目 README（理解 Unigram 语言模型分词的设计思路）；论文 "Neural Machine Translation of Rare Words with Subword Units"（BPE 应用于 NLP 的奠基性论文之一）。

# 第 05 章　预训练技术体系

## 5.1 预训练在解决什么问题

预训练（Pretraining, PT）的目标是让模型在海量无标注文本上，通过自监督的"预测下一个 Token"任务，学习到语言的语法结构、世界知识、基础推理模式等**通用能力底座**。这是整条训练流水线里投入产出比最"厚重"的一环——一次主流规模模型的预训练，涉及数千亿到数万亿 Token 的数据、数百到数千张 GPU、数周到数月的训练时间，成本可达数百万到数千万美元级别。

对多数读者而言，**从零做预训练并非日常工作**（这类工作集中在少数头部实验室/大厂），但理解预训练的原理和工程要点，对以下几件事至关重要：正确理解 Base Model 与 Chat Model 的能力边界差异；判断"继续预训练（CPT）"这一常见工程手段何时该用；理解分布式训练技术（第 6 章）为什么会被设计成现在这个样子（很多分布式并行策略正是为预训练这种超大规模场景而生）。

## 5.2 预训练的核心训练目标形式

绝大多数现代大模型采用纯粹的**因果语言建模（Causal LM）**目标——即第 2 章介绍的"根据前文预测下一个 Token"，用交叉熵损失训练，不需要人工标注，数据本身既是输入也是标签（把序列错位一位即可构造出"输入-标签"对）：

```
原始序列: [t1, t2, t3, t4, t5]
输入:     [t1, t2, t3, t4]
标签:     [t2, t3, t4, t5]     # 每个位置的"标签"就是下一个 token
```

这一设计的优雅之处在于：一条长度为 N 的序列，可以一次前向传播中同时构造出 N-1 个训练样本（每个位置都在预测它的下一个 Token），是预训练能够高效利用海量数据的关键工程基础。历史上也存在其他预训练目标形式（如 BERT 使用的 Masked Language Modeling 掩码语言建模、T5 使用的 Span Corruption 片段掩码还原），但在生成式大模型主导的当下，纯因果语言建模已成为绝对主流，本手册后续默认以此为背景展开。

## 5.3 稠密模型（Dense）与混合专家模型（MoE）

**稠密模型**：每次前向传播，输入都会流经模型的全部参数（传统意义上的"标准"Transformer）。

**混合专家模型（Mixture-of-Experts, MoE）**：把 FFN 层替换为多个并行的"专家"子网络，每个 Token 只会被路由到其中一小部分专家（通常 top-1 或 top-2）参与计算，而非流经全部专家：

```
输入 Token 的隐藏状态
      │
      ▼
┌───────────────┐
│  路由门控网络   │  ← 计算该 Token 与每个专家的匹配分数
│ (Router/Gate)  │
└───────┬────────┘
        │ 选出 top-K 个专家
        ▼
┌─────┐ ┌─────┐ ┌─────┐        ┌─────┐
│专家1 │ │专家2 │ │专家3 │  ...   │专家N │   （只有被选中的 K 个参与实际计算）
└──┬──┘ └──┬──┘ └─────┘        └─────┘
   └──────┬─────
          ▼
   加权求和得到该 Token 的输出
```

MoE 的核心价值在于**用可控的"激活参数量"（每次前向实际参与计算的参数）换取更大的"总参数量"**（模型的知识容量），即以接近稠密模型的推理/训练计算成本，获得远超稠密模型的参数容量与知识存储能力。代价是：需要额外的**负载均衡损失（Load Balancing Loss）**来防止路由退化为"只偏爱少数几个专家、其余专家几乎从不被选中训练"这一常见的 MoE 训练病理现象；分布式训练需要额外引入**专家并行（Expert Parallelism, EP）**这一并行维度（第 6 章）；工程实现复杂度显著高于稠密模型。近两年 MoE 架构（如 DeepSeek-MoE、Mixtral 等代表性工作）已成为追求"性价比最优"的大模型路线的主流选择之一。

## 5.4 训练稳定性：预训练阶段最核心的工程挑战

预训练动辄数周的连续训练过程中，最令人头疼的问题是**训练不稳定**——梯度或 Loss 突然出现异常尖峰（Loss Spike）甚至直接变为 NaN，导致训练发散、被迫从更早的 Checkpoint 回滚重跑，浪费大量计算资源。常见成因与对应工程手段：

| 成因 | 应对手段 |
|---|---|
| 学习率过大/预热不充分 | 更长的 Warmup 阶段、更保守的峰值学习率 |
| 某个 batch 恰好包含异常数据（如极端重复、乱码片段未被清洗干净） | 梯度裁剪、数据质量过滤前置（第 3 章） |
| 混合精度数值溢出 | 采用 BF16 而非 FP16、关键计算保留 FP32 精度 |
| 模型深度增加带来的深层网络训练难题 | Pre-Norm 结构、合理的参数初始化策略 |
| 分布式训练中的数值不确定性/硬件故障导致的静默数据损坏 | 定期健康检查、Checkpoint 频率提高以降低回滚损失 |

工业界的一个重要经验总结是：**预训练工程的相当一部分精力，实际花在"监控与快速响应训练异常"上，而非模型架构本身的设计**——第 10 章会具体讲解如何通过 Loss 曲线、梯度范数等信号做日常监控。

## 5.5 继续预训练（Continued Pretraining, CPT）

CPT 指在一个已经训练好的 Base Model 基础上，用新的语料（通常是特定领域，如医疗、法律、金融文本，或者新增语种）继续做因果语言建模训练，目的是**在不从零开始的前提下，为模型注入新的领域知识或语言能力**。CPT 相比从零预训练的资源需求低得多，是很多企业级"垂直领域大模型"项目的实际技术路线（相比 SFT，CPT 更适合"灌输大量新知识"这一目标，因为 SFT 阶段的数据量级通常远不足以让模型充分学习大量新的事实性知识——这也呼应了第 3 章提到的 LIMA 论文核心论点：SFT 更擅长"激活/校正已有能力的表达方式"，而非"灌输大量新知识"）。

CPT 需要特别注意的两个工程细节：**灾难性遗忘（Catastrophic Forgetting）**——只用新领域数据继续训练，容易导致模型在原有通用能力上出现明显退化，常见缓解手段是在 CPT 数据中混入一定比例的通用语料（Replay/数据回放）；**学习率的重新设置**——CPT 通常需要比原始预训练更小的学习率，并同样需要一个（相对更短的）Warmup 阶段，直接沿用极小的"尾声阶段"学习率或者过大的学习率都容易导致效果不佳。

## 5.6 预训练效果的早期评估

由于预训练周期长、成本高，通常会在训练过程中定期（如每隔固定步数）在一个小规模的、有代表性的评测集合上进行验证，常用信号包括：**验证集困惑度（Validation PPL）**的下降趋势是否符合预期（是否接近同等计算量下的 Scaling Law 预测曲线）；少量核心下游能力基准（如常识问答、基础数学题）的**零样本（Zero-shot）/少样本（Few-shot）能力**是否随训练进程正常提升。这与 SFT/RLHF 之后的下游能力评测（第 10 章）在方法论上是相通的，区别主要在于预训练阶段更关注"通用能力是否正常涌现"而非"某个具体任务是否达标"。

## 5.7 本章小结与学习建议

预训练是理解"大模型能力从何而来"最根本的一层，但对大多数实际工作场景而言，更常打交道的是"如何在别人预训练好的 Base Model 上做好 CPT/SFT/对齐"。建议的学习策略是：理解本章原理性内容即可，不必强求亲自跑通一次真正的大规模预训练（除非工作性质确实需要），把更多实践精力投入到第 6-8 章的分布式训练与微调/对齐技术上。

推荐资料：论文 "GPT-3: Language Models are Few-Shot Learners"（理解 Few-shot 能力与规模的关系）；DeepSeek 系列技术报告（近年对训练稳定性、MoE 工程细节公开程度较高的一手资料）；LLaMA 系列技术报告（了解现代主流架构选择背后的消融实验依据）；nanoGPT 开源项目（Andrej Karpathy 出品，用最精简的代码复现 GPT-2 级别预训练全流程，是建立预训练"手感"的最佳实战起点，第 15 章会作为推荐实战项目之一详细展开）。

# 第 06 章　分布式训练技术

## 6.1 为什么必须做分布式训练

一个 70 亿参数的模型，仅模型权重本身用 BF16 存储就需要约 14GB 显存；加上 AdamW 优化器状态（一阶动量、二阶动量，通常用 FP32 存储，约为参数量的 8 倍字节数）、梯度、激活值，全参数训练一个 7B 模型的显存需求轻松突破 100GB，远超单张消费级/主流数据中心 GPU 的显存容量（如 A100/H100 单卡 80GB）。这就是分布式训练技术存在的根本原因：**把"装不下的模型/数据"切分到多张卡、多台机器上协同计算**。理解分布式训练，本质上是理解"到底在切分什么"以及"切分之后如何协调通信"。

## 6.2 数据并行（Data Parallelism, DP）：最基础的并行维度

**朴素数据并行**：每张卡上都保存一份完整的模型副本，不同卡处理不同的数据批次，前向/反向传播各自独立计算，只在每一步更新参数前，通过 **All-Reduce** 通信操作把所有卡上的梯度做平均，再各自用平均后的梯度更新本地模型副本：

```
GPU 0: 完整模型副本 + 数据batch_0 → 计算梯度 g0
GPU 1: 完整模型副本 + 数据batch_1 → 计算梯度 g1
GPU N: 完整模型副本 + 数据batch_N → 计算梯度 gN
              │
              ▼  All-Reduce（所有GPU间通信，求平均梯度）
        平均梯度 g_avg = (g0+g1+...+gN)/N
              │
              ▼
     每张GPU各自用 g_avg 更新自己的模型副本（更新后所有副本保持一致）
```

朴素数据并行的问题是**每张卡都要存一份完整的模型 + 优化器状态**，显存浪费严重，对大模型而言这部分冗余存储本身就可能超出单卡显存容量——这就引出了 **ZeRO（Zero Redundancy Optimizer）** 这一关键技术。

### 6.2.1 ZeRO：消除数据并行中的显存冗余

ZeRO（DeepSpeed 提出）的核心思想是：**既然所有卡上的优化器状态/梯度/参数本质上是冗余的，那就把它们分片存储到不同卡上，需要用到时再临时通信获取**，分为三个递进阶段：

| ZeRO Stage | 分片对象 | 显存节省 | 通信开销 |
|---|---|---|---|
| Stage 1 | 仅分片优化器状态 | 较少 | 最低 |
| Stage 2 | 分片优化器状态 + 梯度 | 中等 | 略增加 |
| Stage 3 | 分片优化器状态 + 梯度 + 模型参数本身 | 最大（等效于把整个模型"拆开"存在多卡上） | 最高（每次前向/反向都需要临时收集完整参数） |

```
ZeRO Stage 3 伪代码思想：
for each_gpu_rank in range(N):
    keep only 1/N of (parameters, gradients, optimizer_states) locally

在前向传播需要某一层完整参数时：
    all_gather(该层参数分片, from=所有GPU) → 临时拼出完整参数 → 用完即释放
```

ZeRO 与 **FSDP（Fully Sharded Data Parallel，PyTorch 原生实现的类似理念方案）** 是目前最广泛使用的"通过分片消除数据并行冗余"技术，二者理念高度一致，是大多数中小规模（单机到几十张卡）全参数训练/微调任务的首选方案，因为它们**对用户暴露的编程接口相对简单**（相比下面要介绍的张量并行/流水线并行，几乎不需要对模型代码做结构性改造）。

## 6.3 张量并行（Tensor Parallelism, TP）

当模型单层的参数矩阵本身就大到一张卡放不下时（或者即便放得下，ZeRO Stage 3 频繁的参数收集通信在超大规模集群下开销过高），需要把**单个矩阵运算本身切开**，分布到多张卡上协同完成：

```
一个线性层 Y = X @ W，把权重矩阵 W 按列切成两半 [W_a | W_b]
GPU 0: 计算 Y_a = X @ W_a
GPU 1: 计算 Y_b = X @ W_b
最终结果: Y = concat(Y_a, Y_b)   （某些切法需要在此处插入一次通信操作做结果聚合）
```

张量并行的通信频率远高于数据并行（几乎每一层内部都需要通信），因此**通常只在同一台物理机内、通过高速互联（如 NVLink）连接的多张卡之间使用**，跨机器做张量并行的通信延迟代价往往难以接受。这是理解"3D 并行为什么要分层设计"的关键——不同并行维度对通信带宽的敏感度差异巨大，需要与物理网络拓扑匹配。

## 6.4 流水线并行（Pipeline Parallelism, PP）

把模型按"层"切分成若干段，每一段（Stage）放在不同的卡上，数据像流水线一样依次流经各段：

```
GPU 0: 第 1-8 层    GPU 1: 第 9-16 层    GPU 2: 第 17-24 层   GPU 3: 第 25-32 层
   输入 → [计算] → 中间结果 → [计算] → 中间结果 → [计算] → 中间结果 → [计算] → 输出
```

朴素流水线并行存在"气泡（Bubble）"问题——在某一时刻，只有一张卡在实际计算，其余卡都在空闲等待上下游数据。解决方案是把一个大 Batch 切成多个 **Micro-Batch**，让不同 Micro-Batch 在流水线的不同阶段"错峰"并行处理（类似工厂流水线让多个工件同时处于不同工序）：

```
朴素方式（气泡巨大）：
GPU0: [===计算===]                                    (其余时间空闲)
GPU1:              [===计算===]                       (其余时间空闲)
GPU2:                           [===计算===]

切分 Micro-Batch 后（气泡显著减少）：
GPU0: [mb1][mb2][mb3][mb4]
GPU1:      [mb1][mb2][mb3][mb4]
GPU2:           [mb1][mb2][mb3][mb4]
```

常见的流水线调度策略（如 GPipe 式、1F1B 式、Megatron 提出的 Interleaved 式调度）本质上都是在优化"如何排布不同 Micro-Batch 在不同 Stage 的执行时序，把气泡压到最小"这一问题，具体调度算法细节属于可以进一步深挖的专题，此处建立"流水线并行存在气泡问题、需要靠 Micro-Batch 切分与调度算法缓解"这一核心认知即可。

## 6.5 序列并行（Sequence Parallelism, SP）与上下文并行（Context Parallelism, CP）

**序列并行**：张量并行方案中，某些操作（如 LayerNorm/Dropout）沿"序列长度"维度天然是可以独立并行的（不像矩阵乘法那样需要跨卡通信聚合），SP 正是利用这一点，把这部分计算也按序列维度切分到多卡，进一步降低单卡的激活值显存占用，通常与 TP 搭配使用。

**上下文并行**：专门针对"超长上下文训练"场景——当序列长度本身达到数十万 Token 级别时，即便模型参数能放进一张卡，仅仅是存储该长序列对应的**注意力计算中间结果（尤其是 KV 相关的激活值）**也会超出显存容量，CP 把同一条长序列本身，沿长度维度切分到多张卡上分别计算注意力，再通过通信协调获得完整的注意力结果。这是近两年"长上下文模型"训练热潮中新兴的重要并行维度，随附 ms-swift 文档中提到的 Megatron-SWIFT 对 CP 的支持，正是应对这一需求。

## 6.6 专家并行（Expert Parallelism, EP）

专用于 MoE 架构（第 5 章）——把不同的"专家"子网络分布存放到不同卡上，每张卡只负责计算被路由到本卡专家的那部分 Token，需要额外的 **All-to-All** 通信操作把 Token 路由到其所属专家所在的卡、再把计算结果路由回原来的卡。

## 6.7 3D/4D/5D 并行：组合的艺术

实际的超大规模训练任务，往往同时组合使用上述多个并行维度（业界常说"3D 并行"指 DP+TP+PP 的组合，加上 SP/CP/EP 后有时被称为更高维度的并行），如何在给定的 GPU 集群拓扑（机内高速互联、机间较慢互联）下为每个维度分配"并行度"，是一个需要结合模型结构、集群硬件拓扑、通信带宽做综合权衡的复杂工程决策，通常遵循这样的直觉原则：

```
并行维度选择的经验直觉（通信开销从高到低排序，对应优先安排在通信更快的范围内）：
TP（张量并行）   → 通信最频繁 → 优先安排在同机内 NVLink 高速互联的卡之间
SP/CP           → 通信较频繁 → 同样优先安排在机内
PP（流水线并行） → 通信相对稀疏（只在 Stage 边界通信）→ 可以跨机器安排
DP（数据并行/ZeRO）→ 通信频率最低（可以做梯度累积、降低同步频率）→ 最适合跨机器、大规模扩展的维度
EP（专家并行）    → 通信模式特殊（All-to-All），需结合具体集群拓扑与 MoE 路由特性专门优化
```

## 6.8 激活值重计算（Activation Recomputation / Gradient Checkpointing）

一个与"并行策略"正交、但同样重要的显存优化技术：训练时反向传播需要用到前向传播过程中每一层的中间激活值来计算梯度，若把所有中间激活值都保留在显存中，占用会随层数线性增长；激活值重计算的思路是**前向传播时只保留少数几个"检查点"层的激活值，其余层的激活值在反向传播需要用到时，现场重新做一次前向计算得到**，用"额外一次前向计算的时间成本"换取"大幅降低激活值显存占用"，是几乎所有大模型训练框架的标配选项。

## 6.9 分布式训练框架生态一览（承接第 9 章详细展开）

本章介绍的并行策略，在实际工程中分别由不同的框架/组件承载实现：**DeepSpeed**（以 ZeRO 系列著称，也支持 3D 并行）、**Megatron-LM/Megatron-Core**（NVIDIA 出品，以高效的 TP/PP/SP/CP/EP 实现著称，是超大规模预训练的事实工业标准之一，随附 ms-swift 文档第 9 章的 Megatron-SWIFT 子系统正是构建在 megatron-core 之上）、**PyTorch FSDP/FSDP2**（PyTorch 原生的 ZeRO 类实现，与 PyTorch 生态集成度最高）。第 9 章会对这些框架做系统性的选型对比。

## 6.10 本章小结与学习建议

分布式训练是大模型训练区别于传统训练"工程硬核程度"最高的部分，也是最需要动手实践才能真正内化的部分——单纯阅读原理很难建立起对"通信开销、显存占用、并行度配置"三者权衡的直觉。建议的学习路径是：先用 2-4 张卡做 ZeRO/FSDP 的朴素数据并行实践（门槛最低），再逐步尝试引入 TP/PP 的组合训练（需要更多卡或云上按需资源），过程中重点观察不同配置下的显存占用与吞吐量（Tokens/秒）变化。

推荐资料：论文 "ZeRO: Memory Optimizations Toward Training Trillion Parameter Models"、"Megatron-LM: Training Multi-Billion Parameter Language Models Using Model Parallelism"、"GPipe" 与 "PipeDream"（流水线并行奠基工作）；HuggingFace 出品的免费电子书/博客 "The Ultra-Scale Playbook"（系统性梳理各类并行策略与工程实践，是近年该领域公认质量很高的免费中文/英文学习资料之一）；DeepSpeed 与 Megatron-LM 官方文档中的架构说明部分。

# 第 07 章　有监督微调与参数高效微调（PEFT）

## 7.1 SFT 的定位再确认

承接第 1、5 章的讨论：SFT 的核心作用是让预训练得到的 Base Model（本质上只是一个"续写"模型）学会以对话/指令遵循的形式组织其已有能力的输出——从"给一段话接着往下写"转变为"理解一个指令、给出针对性的回答"。这一转变在实现层面主要体现为**训练数据格式（多轮对话结构）+ Loss Masking（只对助手回复部分计算损失）**的组合（第 2、4 章已介绍），本章聚焦"用什么资源投入方式完成这次训练"这一问题。

## 7.2 全参数微调 vs 参数高效微调：核心决策

**全参数微调（Full Fine-Tuning）**：更新模型的全部参数。效果上限最高（尤其当微调数据量较大、任务与预训练分布差异较大时），但资源需求几乎等同于"更小规模的预训练"——需要保存全部参数的梯度与优化器状态，第 6 章介绍的分布式并行技术往往是全参数微调大模型的必需品，而非可选项。

**参数高效微调（Parameter-Efficient Fine-Tuning, PEFT）**：冻结 Base Model 绝大部分参数，只新增/更新一小部分参数（通常占总参数量的 0.1%-几个百分点）。核心价值在于**用远低于全参数微调的显存与计算成本，达到接近全参数微调的效果**（在很多任务上，尤其是"教会模型遵循某种输出格式/风格"这类任务，PEFT 的效果与全参数微调相差无几；但在"需要注入大量新知识"这类任务上，PEFT 的效果上限通常不及全参数微调或 CPT）。

## 7.3 LoRA：当前最主流的 PEFT 方法

**核心思想**：假设模型微调过程中，参数的"变化量"（而非参数本身）本质上是低秩的（即这个变化矩阵可以用两个更小的矩阵相乘来近似表示），因此不直接微调原始权重矩阵 W，而是冻结 W，额外引入两个低秩矩阵 A（降维）和 B（升维）来近似表示权重的更新量：

```
原始前向传播: Y = X @ W                    （W 被冻结，不参与梯度更新）

LoRA 改造后:  Y = X @ W + X @ A @ B  * scale
              其中 A 的形状为 (d, r)，B 的形状为 (r, d)，r 远小于 d （r 称为"秩"，Rank）
              只有 A、B 参与梯度更新，W 依然冻结不变

参数量对比（举例 d=4096, r=8）：
  原始 W：  4096 × 4096 ≈ 1670 万参数
  LoRA A+B： 4096×8 + 8×4096 ≈ 6.5 万参数   （约为原始的 0.4%）
```

LoRA 的工程优势非常突出：训练时只需要为 A、B 这一小部分参数保存优化器状态，显存占用大幅降低；推理部署时，A@B 可以直接与原始 W **合并（Merge）** 成一个新的权重矩阵，合并后的模型结构与原始 Base Model 完全一致，不会引入任何额外的推理延迟——这也是为什么 LoRA 能够"训练时省资源、部署时零额外开销"两头兼顾，成为 PEFT 领域事实标准的核心原因。

**秩 r 的选择**：r 越大，可训练参数越多，理论拟合能力越强，但也越接近全参数微调的资源需求与过拟合风险；r 越小，训练越轻量，但可能欠拟合复杂任务。实践中 r 通常在 8 到 256 之间按任务复杂度与数据量选择，是需要结合具体任务做实验调整的超参数。

## 7.4 QLoRA：进一步压缩显存占用

**核心思想**：在 LoRA 基础上，把被冻结的原始权重 W 用**低比特量化**（通常是 4-bit）的形式存储在显存中（只在实际计算时临时反量化为可计算的精度），而参与训练的 LoRA 低秩矩阵 A、B 依然保持较高精度：

```
显存占用对比（以 7B 模型为例，量级示意）：
  全参数微调：  权重(14GB, bf16) + 优化器状态(~112GB) + 梯度(~14GB) ≈ 140GB+
  LoRA：       权重(14GB, bf16, 冻结不需要优化器状态) + 极小的A/B优化器状态 ≈ 15GB左右
  QLoRA：      权重(约3.5GB, 4bit量化) + 极小的A/B优化器状态 ≈ 5GB左右
```

QLoRA 的核心工程贡献之一是提出了针对量化误差的补偿技术（如分块量化、双重量化等），使得"用 4-bit 存储权重"这一激进压缩手段，在实际微调效果上依然能够接近全精度 LoRA 的表现，让"单张消费级显卡微调百亿参数级模型"成为现实，是资源受限场景下的重要技术选择。

## 7.5 DoRA 与其他 PEFT 变体

**DoRA（Weight-Decomposed Low-Rank Adaptation）**：在 LoRA 基础上，把权重矩阵分解为"大小（Magnitude）"和"方向（Direction）"两个独立分量分别处理——直觉上是让 LoRA 的低秩更新能够更灵活地同时调整参数的"幅度"与"方向"这两个此前被耦合在一起处理的属性，多数场景下相比标准 LoRA 有小幅稳定的效果提升，训练与推理成本与 LoRA 基本相当。

其他值得了解名称与思路（本手册不逐一展开细节）：**Prefix Tuning/P-Tuning**（在输入序列前额外拼接一段可训练的"虚拟 Token"向量，冻结模型本体，只训练这段前缀）；**(IA)³**（通过学习对激活值做逐元素缩放的方式实现轻量适配）；这些方法在 LoRA 系列成为事实标准后，实际工程使用频率已明显下降，但了解其存在与核心思路，有助于理解 PEFT 这一研究方向的技术演进脉络与设计空间全貌。

## 7.6 混合调优：不同模块采用不同策略

第 6 章的并行策略是"如何切分计算"，本节的"混合调优"则是"模型的不同部分，采用不同的冻结/训练策略组合"——例如全部用 LoRA、但某些关键层（如 Embedding 层、LM Head 输出层）额外设置为全参数可训练；或者在多模态模型中对视觉编码器（ViT）、对齐模块（Aligner）、语言模型主干（LLM）三部分分别独立设置冻结策略（随附 ms-swift 文档第 17 章对此有具体实现层面的详细说明，`--freeze_vit`/`--freeze_aligner`/`--freeze_llm` 三个开关的执行逻辑值得直接参照该文档理解）。

## 7.7 SFT 训练中的常见问题与调优思路

**灾难性遗忘**：微调后模型在原本擅长的通用任务上出现能力退化，常见缓解手段：控制学习率不宜过大、控制微调数据量与训练轮数（Epoch）不宜过多（大模型 SFT 阶段的训练轮数通常远少于传统小模型，1-3 个 Epoch 是常见范围，远多于此容易导致过拟合与遗忘加剧）、在微调数据中混入少量通用能力数据做"回放"。

**格式过拟合（模型"学会"了表面的回复格式，但底层能力没有真正提升）**：这通常是 SFT 数据本身同质化程度过高的信号，需要回到第 3 章的数据工程环节，提升数据的多样性。

**多任务微调中的任务间冲突（一个任务学好了、另一个任务却退步了）**：常见应对思路包括调整不同任务数据的采样权重、采用更保守的学习率、必要时考虑针对不同任务分别训练不同的 LoRA 适配器而非追求单一模型多任务全能。

## 7.8 本章小结与学习建议

SFT/PEFT 是目前大模型微调工作中**上手门槛最低、实践反馈最快**的部分——用一张消费级显卡 + QLoRA，就足以在几小时内完成一次完整的微调实验并观察效果变化，是建议所有读者最优先动手实践的技术环节（第 15 章会给出具体的实战项目建议）。

推荐资料：论文 "LoRA: Low-Rank Adaptation of Large Language Models"、"QLoRA: Efficient Finetuning of Quantized LLMs"、"DoRA: Weight-Decomposed Low-Rank Adaptation"；HuggingFace PEFT 库文档（覆盖各类 PEFT 方法的概念性说明与对比）；具体的框架级实操，建议直接参照随附的 ms-swift 文档第 6 章（Tuner 插件体系）。

# 第 08 章　对齐训练：RLHF/DPO/GRPO 体系

## 8.1 为什么 SFT 之后还需要对齐训练

SFT 教会模型"如何组织回答的形式"，但没有解决一个更精细的问题：**在多个都"形式正确"的候选回答之间，模型应该更偏好哪一个？** 例如，同一个问题可能有多个语法正确、指令遵循度都不错的回答，但其中某个回答更简洁、更安全、更符合人类的实际偏好——SFT 的训练目标（对唯一的标注答案做交叉熵）没有能力表达"相对偏好"这种更细粒度的信号，这正是对齐训练（Alignment Training）要解决的问题。近两年，对齐训练的范畴进一步扩展到"提升模型的推理能力"这一目标（以 GRPO 为代表的技术路线），本章会覆盖这两条脉络。

## 8.2 RLHF 经典范式：三阶段流程

传统意义的 RLHF（以 InstructGPT 论文确立的范式为代表）包含三个阶段：

```
阶段一：SFT（第7章已覆盖）
   Base Model → SFT Model

阶段二：训练奖励模型 (Reward Model, RM)
   人工标注员对同一问题的多个候选回答做偏好排序（"回答A比回答B更好"）
   用这些偏好数据训练一个"打分模型"：输入(问题,回答) → 输出一个标量分数
   目标：让 RM 对人类更偏好的回答给出更高分数

阶段三：用强化学习（PPO算法）优化策略模型
   策略模型（初始化自SFT Model）对问题生成回答
        │
        ▼
   奖励模型 RM 对生成的回答打分，作为强化学习的"奖励信号"
        │
        ▼
   用 PPO 算法更新策略模型参数，让它更倾向于生成能获得RM高分的回答
   （同时用一个 KL 散度惩罚项，约束策略模型不要偏离SFT Model太远，
    防止"钻营高分但语言退化/答非所问"这类奖励作弊现象）
```

**PPO（Proximal Policy Optimization，近端策略优化）** 是强化学习领域的经典算法，在 RLHF 场景下需要同时维护策略模型、奖励模型、价值模型（Critic，估计当前状态的期望回报）、以及一个冻结的参考模型（Reference Model，用于计算 KL 惩罚项）—— **这四个模型同时存在、同时占用显存**，是传统 PPO 式 RLHF 工程复杂度极高、资源消耗极大的核心原因。

## 8.3 DPO：绕开显式奖励模型与强化学习的直接优化方案

**DPO（Direct Preference Optimization）** 的核心洞察是：可以从数学上证明，PPO 式 RLHF 优化目标的最优解，与"直接在偏好数据对上做一种特殊形式的对比学习"这一更简单的监督学习目标是等价的——也就是说，**不需要显式训练一个独立的奖励模型，也不需要跑真正的强化学习采样过程，只需要用偏好数据（"回答A优于回答B"这样的成对数据）直接优化策略模型**：

```
DPO 训练数据形式: (问题, 更优回答 chosen, 更差回答 rejected)

DPO 损失函数（思想示意，非精确公式）：
loss = - log( sigmoid(
    beta * [ (策略模型给chosen的对数概率 - 参考模型给chosen的对数概率)
           - (策略模型给rejected的对数概率 - 参考模型给rejected的对数概率) ]
))

直觉：鼓励策略模型相对于参考模型，进一步提高"更优回答"的生成概率、
     同时进一步降低"更差回答"的生成概率，beta 控制这一调整力度的强弱
```

DPO 的工程价值在于**把强化学习问题转化为了一个形式上接近 SFT 的监督学习问题**，只需要维护策略模型与一个冻结的参考模型两份显存占用，训练流程也不再需要在线采样（Rollout），大幅降低了对齐训练的工程复杂度与资源门槛，这也是为什么 DPO 自提出后迅速成为工业界应用最广泛的对齐训练方法之一。

## 8.4 DPO 家族的进一步演化

DPO 提出后，学术界针对其一些局限性提出了大量变体，理解其"分别改进了 DPO 的什么问题"即可，不需要记住所有公式细节：

| 方法 | 相对 DPO 的核心改进思路 |
|---|---|
| IPO | 针对 DPO 在偏好数据存在噪声/矛盾时容易过拟合的问题，引入正则化改进优化目标形式 |
| KTO | 不要求数据必须是"成对偏好比较"的形式，只需要"这个回答是好是坏"这种更容易获取的单点标注，降低数据构造门槛 |
| ORPO | 把 SFT 与偏好对齐这两个原本分开的阶段合并为一步训练完成，简化训练流程 |
| SimPO | 去掉了 DPO 需要额外维护参考模型这一开销，用回答的平均对数概率长度归一化后的差值直接构造优化目标，进一步降低工程与显存成本 |

## 8.5 GRPO 与推理模型的兴起：对齐训练的新前沿

**GRPO（Group Relative Policy Optimization）** 是近年（尤其伴随 DeepSeek-R1 等推理模型的公开技术报告）被广泛关注的强化学习算法，核心动机是**去掉传统 PPO 中开销很大的价值模型（Critic）**，转而用"同一个问题的一组（Group）采样结果之间的相对好坏"来估计优势（Advantage），从而大幅简化训练所需的模型数量与资源：

```
GRPO 核心流程（思想示意）：
对同一个问题 q，让当前策略模型采样生成一组（如 8-16 个）不同回答 [o1, o2, ..., oG]
        │
        ▼
用规则化奖励函数或奖励模型，分别给这组回答打分 [r1, r2, ..., rG]
（在数学/代码等有明确对错标准的任务上，常直接用"答案是否正确"这类规则化奖励，
 而非训练一个额外的神经网络奖励模型——这大幅降低了Reward Hacking的风险）
        │
        ▼
计算组内相对优势: advantage_i = (r_i - mean(r1...rG)) / std(r1...rG)
（每个回答的优势，由它相对于"同一问题下这一组其他回答"的相对表现决定，
 而不再需要一个独立的价值模型来估计绝对的期望回报）
        │
        ▼
用类似PPO的策略梯度更新方式，结合上述优势值更新策略模型
（同样保留KL惩罚项约束，防止策略模型偏离参考模型过远）
```

GRPO 因为放弃了价值模型，只需要维护策略模型 + 参考模型（部分实现中参考模型甚至可以省略或用更轻量方式处理）+ 奖励计算，工程复杂度介于 DPO 与传统 PPO 之间，但因为保留了"真正在线采样"这一强化学习的核心特性，相比 DPO 这种"纯离线偏好学习"方法，**在提升复杂多步推理能力（如数学证明、代码调试这类需要模型自主探索多种解题路径的任务）上展现出更强的效果**，是当前"推理模型"训练路线的核心技术支柱。GRPO 之后，学术界又提出了一批同源变体（如 DAPO、GSPO、RLOO、Reinforce++ 等），大多是针对 GRPO 在训练稳定性、采样效率、优势估计方式等方面的进一步改进，建议在掌握 GRPO 核心思想后，把这些变体作为"选修深入"内容按需查阅对应论文。

## 8.6 Rollout 基础设施：训练与推理的第一次深度耦合

GRPO/PPO 这类"在线"强化学习方法，要求在训练过程中，让当前策略模型**实时生成大量采样样本（Rollout）**用于计算奖励与优势——这一生成过程如果直接用训练框架自带的朴素生成逻辑，效率远不及专门的推理引擎（vLLM/SGLang 等，具备 Continuous Batching、KV Cache 管理等推理优化技术，第 12 章详述），因此现代 RLHF/GRPO 训练框架普遍会**把专门的推理引擎集成进训练循环**，用于加速 Rollout 环节，这也是随附 ms-swift 文档第 8 章提到"vLLM colocate/server 两种 Rollout 模式"的技术背景所在。这一设计带来一个新的工程挑战：**权重同步**——策略模型在训练侧每更新一步参数，都需要及时同步给负责 Rollout 的推理引擎实例，否则采样用的策略与实际训练更新的策略会产生不一致（Off-Policy 问题）。这是"训练与推理边界模糊化"（第 1 章提到的心智转变之一）最具体的技术体现。

## 8.7 奖励设计与 Reward Hacking

**奖励模型型（Model-based Reward）**：适合"好坏难以用简单规则判定"的开放式任务（如创意写作、开放对话），但存在被"钻空子"的风险——策略模型可能学会某些能骗取奖励模型高分、但实际质量并不高的输出模式（如故意增加回答长度、堆砌特定关键词），这被称为 **Reward Hacking（奖励作弊/奖励破解）**，是对齐训练领域最核心的挑战之一，常见缓解手段包括：适度加强 KL 惩罚约束、对奖励模型本身做对抗性数据增强训练、引入多个不同角度的奖励信号做加权组合而非依赖单一奖励模型。

**规则化奖励（Rule-based Reward）**：适合"好坏有明确客观标准"的任务（如数学题答案是否正确、代码是否通过单元测试），因为不依赖一个可能被"欺骗"的神经网络打分器，Reward Hacking 风险显著更低，这也是为什么当前推理模型训练路线（数学、代码等任务）大量采用规则化奖励而非训练额外的奖励模型。**过程奖励模型（Process Reward Model, PRM）** 与**结果奖励模型（Outcome Reward Model, ORM）** 的区分则在于：ORM 只对最终答案对错打分，PRM 尝试对推理过程中的每一个中间步骤分别给出质量评价——PRM 理论上能提供更细粒度的训练信号，但标注成本与训练难度也显著更高，是否值得投入取决于具体任务与资源预算。

## 8.8 本章小结与学习建议

对齐训练是当前大模型研究领域技术演进最活跃、论文更新最快的方向，建议的学习策略是"先扎实掌握 DPO（工程门槛最低、原理最容易理解）与 GRPO（当前推理模型训练的核心）这两个当前最主流的方法，再以此为基础，按需查阅同源的变体论文"，不必追求穷尽所有历史上出现过的对齐算法名称。

推荐资料：论文 "Training language models to follow instructions with human feedback"（InstructGPT，RLHF 经典范式奠基论文）、"Direct Preference Optimization: Your Language Model is Secretly a Reward Model"（DPO 原始论文）、DeepSeek-R1 技术报告（GRPO 在推理模型训练中的公开一手实践资料，对理解规则化奖励与推理能力训练的关系极具参考价值）；具体框架实现建议参照随附 ms-swift 文档第 8 章；开源实践项目：TRL（HuggingFace 出品，DPO/PPO/GRPO 等算法的参考实现，代码可读性较高，适合作为深入理解算法细节的阅读对象）。

# 第 09 章　训练框架生态导览

## 9.1 为什么需要"框架"而不是从零手写训练循环

前面几章介绍的分布式并行策略、PEFT 方法、对齐算法，如果每次训练任务都要从零手写实现，工程成本极高且极易出错（尤其是分布式通信部分，涉及大量底层工程细节）。训练框架的价值在于**把这些通用能力封装为可复用、可组合的组件**，使用者只需要通过配置/命令行参数选择需要的能力组合，而不必关心底层实现。理解不同框架各自的"能力定位"与"设计取舍"，是做技术选型的前提。

## 9.2 框架生态全景分类

按照"关注的核心能力层次"，可以把当前主流训练框架/库大致分为几个层次：

```
┌─────────────────────────────────────────────────────────┐
│  第一层：底层分布式引擎（提供并行策略的核心实现）             │
│  DeepSpeed  /  Megatron-LM（Megatron-Core） /  PyTorch FSDP│
└─────────────────────────────────────────────────────────┘
                          │  被上层封装调用
┌─────────────────────────────────────────────────────────┐
│  第二层：通用训练循环封装库                                 │
│  HuggingFace Transformers Trainer / Accelerate            │
└─────────────────────────────────────────────────────────┘
                          │  被上层进一步封装调用
┌─────────────────────────────────────────────────────────┐
│  第三层：面向特定训练范式的高层库                            │
│  TRL（对齐训练：DPO/PPO/GRPO）                             │
└─────────────────────────────────────────────────────────┘
                          │
┌─────────────────────────────────────────────────────────┐
│  第四层：一站式训练框架（覆盖数据/模型/算法/全流程，开箱即用）│
│  ms-swift / LLaMA-Factory / Axolotl / veRL / OpenRLHF /NeMo│
└─────────────────────────────────────────────────────────┘
```

需要注意这一分层并非绝对——例如 ms-swift 本身既可以直接调用 Megatron-Core（构成随附文档提到的 Megatron-SWIFT 子系统）做超大规模预训练，也提供开箱即用的 SFT/RLHF 高层封装，横跨了第一层到第四层的能力，"一站式框架"的核心竞争力正在于**把底层的分布式引擎与上层的算法实现打通、提供统一简洁的使用体验**。

## 9.3 底层分布式引擎对比

| 框架 | 核心定位 | 优势场景 | 学习/使用门槛 |
|---|---|---|---|
| DeepSpeed | ZeRO 系列显存优化 + 完整 3D 并行支持 | 中小规模到大规模的全参数训练/微调，尤其是显存受限场景，与 HuggingFace 生态集成度高 | 中等，配置文件（JSON）驱动，较易上手 |
| Megatron-LM / Megatron-Core | 极致优化的 TP/PP/SP/CP/EP 实现，为超大规模预训练而生 | 千卡以上级别的从零预训练、超大规模 CPT | 较高，更偏底层，通常需要额外的桥接层（如各家的 Mcore-Bridge）才能便捷对接 HuggingFace 生态的模型权重格式 |
| PyTorch FSDP/FSDP2 | PyTorch 原生的 ZeRO 类实现 | 与 PyTorch 生态（尤其是较新特性）结合最紧密，社区原生支持，适合追求"少一层封装依赖"的团队 | 中等，随 PyTorch 版本迭代持续改进易用性 |

## 9.4 一站式训练框架对比

| 框架 | 核心特点 | 相对优势 | 需留意的取舍 |
|---|---|---|---|
| ms-swift | ModelScope 出品，模型/多模态覆盖面极广（600+ 纯文本、300+ 多模态），SFT/PEFT/RLHF/Megatron-SWIFT 全流程一体化，国产硬件适配投入大（随附文档第 18 章有详细分析） | 生态活跃、模型支持广度业界领先、多模态与国产硬件场景尤其突出 | 作为一体化框架，深度定制某个非常规训练逻辑时，仍需要理解其内部架构（这正是随附文档存在的价值） |
| LLaMA-Factory | 同样是模型覆盖面广、开箱即用的一站式框架，社区活跃、文档友好，提供 Web UI | 上手曲线平缓，适合快速实验与教学场景 | 面向超大规模分布式训练与前沿 RL 算法的深度定制能力，与专门面向该场景的框架相比存在差距 |
| Axolotl | 面向 LLaMA/Mistral 等主流开源模型系的高质量 SFT/PEFT 框架 | 配置文件简洁清晰，欧美开源社区生态活跃度高 | 模型/多模态覆盖面不及 ms-swift/LLaMA-Factory 广 |
| veRL / OpenRLHF | 专注于大规模 RLHF/GRPO 强化学习训练场景，对 Rollout 基础设施（第 8 章提到的推理引擎集成、权重同步）做了深度优化 | 在超大规模、高吞吐的 RL 训练场景下的工程成熟度与性能通常领先于综合性一站式框架 | 功能聚焦于 RL 阶段，SFT/数据处理等前置环节通常仍需搭配其他工具完成 |
| NVIDIA NeMo | NVIDIA 官方出品，与自家硬件生态（GPU/网络）深度协同优化 | 在 NVIDIA 硬件上的极致性能优化、大规模预训练场景的工业级成熟度 | 相对更偏向 NVIDIA 生态闭环，跨硬件平台的灵活性不是其设计重心 |

## 9.5 一个实用的选型决策框架

面对"该用哪个框架"这一具体问题，建议按以下问题顺序自问自答（而非死记硬背某个框架"更好"）：

1. **我的任务规模是什么？** 单卡/几张卡的 PEFT 微调实验 → 几乎任何一站式框架都能胜任，优先选生态活跃、文档友好的（ms-swift/LLaMA-Factory）；数百卡以上的预训练/大规模 CPT → 需要认真评估 Megatron-Core/NeMo 这类底层引擎的直接使用或对应的一体化封装（如 Megatron-SWIFT）。
2. **我的任务类型是什么？** 常规 SFT/PEFT → 综合性一站式框架足够；重度依赖在线 RL 采样的对齐训练（GRPO 等）→ 优先考虑对 Rollout 基础设施做过专门优化的框架（veRL/OpenRLHF，或 ms-swift 中对应的 RLHF 子系统）。
3. **我的模型是什么？** 冷门/最新发布的模型 → 优先检查各框架对该模型的支持覆盖情况（模型支持广度是 ms-swift/LLaMA-Factory 这类框架的核心卖点之一）；多模态模型 → 同样需要重点核查多模态支持的成熟度与覆盖范围。
4. **我的硬件是什么？** 如果涉及非 NVIDIA 硬件（国产 NPU/GPU 等）→ 需要重点核查目标框架在该硬件平台上的适配文档与社区反馈成熟度，这一点随附 ms-swift 文档第 18 章的硬件适配专题分析提供了很好的分析范例，具备普适的参考价值（同样的评估思路可以套用到其他框架的硬件适配评估上）。
5. **我团队/我个人的既有经验是什么？** 熟悉 HuggingFace 生态（Transformers/Accelerate/PEFT/TRL）→ 从这条技术栈自然延伸出的框架（如直接使用 TRL，或使用与该生态深度集成的一体化框架）学习曲线更平缓。

## 9.6 一个容易被忽视的现实：框架会快速迭代，"底层原理"比"框架 API"更值得投入学习

大模型训练框架生态的迭代速度非常快（新算法、新并行策略几乎每隔几个月就会出现在各框架的更新日志中），这意味着**任何框架的具体 API 用法都存在"半衰期较短"的风险**，而本手册第 1-8 章介绍的原理性内容（分布式并行的核心矛盾、PEFT 的核心思想、对齐算法的核心动机）具有远长于任何单一框架 API 的生命力。这是本手册反复强调"重原理、轻具体代码"这一写作原则背后的现实考量——建议读者把学习精力更多分配在原理理解上，具体框架的使用方式，通过精读该框架的官方文档/专项分析文档（如随附的 ms-swift 文档）在需要时按需掌握，而不必试图"记住"所有框架的所有 API 细节。

## 9.7 本章小结与学习建议

框架选型没有绝对的"最优解"，只有"当前任务与团队背景下的更优解"。建议的学习路径是：先选定一个覆盖面广、文档友好的一站式框架（ms-swift 或 LLaMA-Factory 都是很好的起点）作为"主力工具"深入使用一段时间，建立起"框架内部大致是怎么组织这些能力"的具体认知（随附的 ms-swift 架构分析文档正是这一环节的绝佳学习素材），再根据实际工作中遇到的具体需求（更大规模、更前沿的 RL 算法、特定硬件适配等），按需扩展学习其他专项框架。

推荐资料：各框架的官方文档与 GitHub README 是最新、最权威的一手资料来源（本手册不代替这些文档，只提供"如何比较和选择"的方法论）；HuggingFace 官方博客与文档（Transformers/Accelerate/PEFT/TRL 四件套的概念性介绍，是理解"第二、三层"生态最系统的免费资料）。

# 第 10 章　训练监控、评测与调试

## 10.1 为什么这一章值得单独展开

前面章节讲的是"如何设计与执行一次训练"，本章讲的是"训练跑起来之后，我怎么知道它是不是在朝正确方向前进、出问题了怎么第一时间发现并定位"。这是一项极度依赖实践经验积累的技能——很多资深大模型训练工程师的核心竞争力，恰恰体现在"看一眼 Loss 曲线的形状，就能大致判断出问题出在数据、超参数还是工程实现上"这种经验直觉，本章尝试把这类经验做结构化的梳理。

## 10.2 训练过程监控：应该盯着哪些信号

### 10.2.1 Loss 曲线

最基础但最重要的信号。健康的训练 Loss 曲线通常呈现"整体平滑下降、伴随正常范围内的小幅波动"的形态。需要警惕的异常形态：

```
正常形态：
Loss │╲
     │ ╲___
     │     ╲_____
     │           ╲________
     └──────────────────────→ 训练步数

异常一：Loss Spike（尖峰）
Loss │╲
     │ ╲___    ╱╲  ← 某一步或几步突然剧增，随后可能自行恢复或持续发散
     │     ╲__╱  ╲___
     └──────────────────────→

异常二：Loss 停滞不降
Loss │╲
     │ ╲________________  ← 下降到某个水平后长期不再变化，可能是学习率过小/数据同质化
     └──────────────────────→

异常三：Loss 持续上升发散
Loss │╲          ╱
     │ ╲___     ╱  ← 训练不稳定导致的发散，通常需要回滚到更早checkpoint并调整超参数
     │     ╲___╱
     └──────────────────────→
```

**偶发的 Loss Spike，若能自行快速恢复，通常问题不大**（可能是遇到了某个困难或异常的 batch）；**若 Spike 后持续在高位震荡或不回落，则需要立即介入排查**，常见根因包括学习率过大、梯度裁剪阈值设置不当、混合精度数值溢出、数据中混入了未清洗干净的异常样本。

### 10.2.2 梯度范数（Gradient Norm）

梯度范数的变化趋势是判断"训练是否稳定"的另一个关键信号，通常与 Loss 曲线一起看：梯度范数持续增大、伴随 Loss 上升，是训练即将发散的典型前兆信号，值得设置自动报警及时人工介入。

### 10.2.3 学习率曲线

用于确认实际生效的学习率调度是否与预期设计一致（尤其是断点续训场景下，容易出现学习率调度状态未被正确恢复的工程 Bug，导致续训后学习率突然跳变）。

### 10.2.4 硬件利用率指标

GPU 利用率（是否存在大量计算空闲，可能提示数据加载成为瓶颈，或者分布式并行策略配置存在气泡浪费问题，见第 6 章流水线并行的气泡讨论）、显存占用（是否逼近显存上限，存在因个别异常长样本导致 OOM 崩溃的风险）、网络通信带宽利用率（分布式训练中通信是否成为瓶颈的直接证据）。

## 10.3 常用训练可视化与实验追踪工具

| 工具 | 定位 |
|---|---|
| TensorBoard | 最经典的训练曲线可视化工具，几乎所有训练框架都原生支持 |
| Weights & Biases (WandB) | 功能更全面的实验管理平台，支持多实验对比、超参数扫描记录、团队协作 |
| SwanLab | 国内团队常用的实验追踪工具之一，与 ms-swift 等国内主流框架集成度较好 |

随附 ms-swift 文档第 13 章提到的与 SwanLab/TensorBoard/WandB 的集成，正是上述工具在具体框架中的落地体现。

## 10.4 从"训练内部信号"到"模型能力评测"：为什么需要标准化评测

Loss/PPL 等训练内部信号，反映的是"模型在训练数据分布上拟合得好不好"，并不直接等价于"模型在实际下游任务/真实使用场景中的能力好不好"（第 2 章已提示这一认知误区）。因此，除了训练过程监控，还需要定期在标准化的能力评测基准上给模型"打分"，才能获得关于模型真实能力的可信证据。

## 10.5 常用能力评测基准分类

| 基准类型 | 代表基准 | 评估的能力 |
|---|---|---|
| 综合知识与推理 | MMLU（多学科英文选择题）、C-Eval / CMMLU（中文多学科评测） | 广泛领域的知识掌握与基础推理能力 |
| 数学推理 | GSM8K（小学应用题级别）、MATH（更高难度数学题） | 数值计算与多步推理能力 |
| 代码能力 | HumanEval、MBPP | 代码生成的正确性（通常以"生成代码能否通过单元测试"为评判标准，即 Pass@k 指标） |
| 指令遵循与开放对话质量 | MT-Bench、AlpacaEval | 多轮对话质量、指令遵循精细度，通常依赖 LLM-as-a-Judge（用更强模型或人工评判打分）而非客观正确答案 |
| 安全性与价值观对齐 | 各类安全红队测试集 | 模型是否会输出有害/违规内容、抗越狱攻击的鲁棒性 |

## 10.6 评测方法论：几个容易踩坑的地方

**数据污染**：第 3 章已提到，务必确认评测基准没有意外混入训练数据（尤其是使用大规模网络爬取语料预训练时，一些经典评测基准的题目本身可能就存在于网络语料中）。

**Prompt 格式敏感性**：同一个模型在同一个基准上，因为评测时使用的 Prompt 模板/Few-shot 示例选择方式不同，得分可能有显著差异——这意味着**跨论文/跨团队直接比较评测分数时需要格外谨慎**，最可靠的比较方式是在完全相同的评测框架、相同配置下对比不同模型。

**LLM-as-a-Judge 的局限性**：用更强模型当裁判评价开放式生成质量，是当前应对"无客观标准答案任务"评测难题的主流权宜方案，但存在裁判模型自身偏好偏差（如偏爱更长的回答、偏爱与自己表达风格接近的回答）需要警惕，通常建议结合多个不同的裁判模型、或者搭配一定比例的人工评估交叉验证。

**评测框架/工具**：EvalScope（随附 ms-swift 文档第 12 章提到的评测集成方案）、OpenCompass、lm-evaluation-harness（社区最广泛使用的英文评测标准化工具之一）是当前主流的评测执行工具，价值在于把"评测基准的加载、Prompt 格式、评分逻辑"标准化封装，避免因为评测实现细节的差异导致结果不可比。

## 10.7 训练问题排查的通用思维框架

当训练效果不及预期（如 SFT 之后模型表现变差、RLHF 之后出现明显的 Reward Hacking 迹象）时，建议按下面这条链条依次排查，而非直接怀疑"算法本身有问题"（算法本身往往是学术界经过大量验证的成熟方案，实践中出问题的概率排序通常是：数据 > 超参数配置 > 工程实现细节 > 算法本身）：

```
排查优先级建议：
1. 数据是否有问题？（格式错误、Loss Mask 计算错误、数据分布与预期不符、存在质量低劣或矛盾样本）
2. 超参数配置是否合理？（学习率是否过大/过小、warmup是否充分、batch size是否与学习率不匹配）
3. 工程实现是否有细节疏漏？（分布式并行配置是否正确、混合精度是否有数值问题、断点续训状态是否被正确恢复）
4. 评测方法本身是否可靠？（是否是评测的Prompt格式/数据污染问题，而非模型真的变差了）
5. 才是：算法/方法本身是否真的不适合当前场景（这一层级的怀疑应该放在最后，且需要更严谨的消融实验支撑）
```

## 10.8 本章小结与学习建议

训练监控与调试是一项"越练越准"的经验型技能，最好的学习方式是**在实际训练任务中，养成每天定期查看训练曲线与硬件利用率的习惯**，并对每一次遇到的异常做记录归档（问题现象、排查过程、最终根因、解决方案），逐步积累起自己的"故障案例库"。

推荐资料：各训练框架官方文档中的 FAQ/故障排查章节（往往是最贴近实战、信息密度最高的资料，随附 ms-swift 文档提到的官方 FAQ 就是典型例子）；WandB 官方博客中大量关于"如何解读训练曲线"的实践性文章；lm-evaluation-harness 与 OpenCompass 项目文档（理解标准化评测工具的设计理念）。

# 第 11 章　多模态训练入门

## 11.1 多模态大模型的基本架构范式

当前主流的多模态大语言模型（以图像理解为例）普遍采用"三段式"架构，这与随附 ms-swift 文档第 17 章描述的 ViT/Aligner/LLM 三段划分完全一致：

```
图像输入
   │
   ▼
┌───────────────────┐
│ 视觉编码器 (ViT)     │  ← 通常复用/微调自预训练好的视觉模型（如CLIP的视觉编码器部分）
│                    │     把图像转换为一组"视觉特征向量"
└─────────┬──────────┘
          ▼
┌───────────────────┐
│ 对齐/投影模块        │  ← 通常是一个轻量的MLP或更复杂的重采样结构
│ (Aligner/Projector) │     把视觉特征向量的维度/空间"对齐"到语言模型能理解的embedding空间
└─────────┬──────────┘
          ▼
   视觉Token序列（与文本Token序列拼接/交替排布）
          │
          ▼
┌───────────────────┐
│  语言模型主干 (LLM)  │  ← 与纯文本大模型架构相同，把视觉Token当作"特殊的文本Token"一并处理
└────────────────────┘
```

这一架构设计的核心优雅之处在于：**语言模型主干本身几乎不需要改动**，多模态能力的引入主要体现在"如何把非文本模态转换为语言模型能够理解的Token序列"这一前置转换问题上，这也是为什么第 4 章提到"多模态数据格式相对纯文本格式只是增量扩展"这一设计哲学能够成立的架构基础。

## 11.2 多模态训练的典型分阶段流程

多模态模型的训练通常也分阶段进行，与纯文本模型的 PT→SFT→对齐 三段式有相似的精神内核，但具体阶段划分略有不同：

```
阶段一：对齐预训练 (Alignment Pretraining)
   冻结 ViT 和 LLM 的绝大部分参数，只训练中间的 Aligner/Projector 模块
   （有时也会同步对 LLM 做轻量微调），使用图文对数据（如图像+简单描述）
   目标：让"视觉特征"能够被正确"翻译"进语言模型能理解的embedding空间

阶段二：多模态指令微调 (Multimodal SFT)
   使用图文交替的多轮对话数据（含图像描述、视觉问答、OCR、视觉定位等多种任务类型）
   进一步解冻更多参数参与训练（策略选择见下方"混合调优"讨论）
   目标：让模型学会"理解图像 + 遵循指令 + 按对话格式输出"

阶段三（可选）：多模态对齐训练 (Multimodal RLHF/GRPO)
   参照第8章的对齐训练技术，将其扩展到涉及图像理解的偏好数据/规则化奖励场景
```

## 11.3 多模态数据格式核心设计

承接第 4 章 Chat Template 的讨论，多模态数据格式的核心设计是**在文本 `messages` 的 content 中插入占位符标记**（如 `<image>`），并在样本中额外提供图像的实际路径/URL 字段，训练框架的数据处理层负责把"占位符"替换/展开为"该图像实际编码出的视觉Token序列"：

```
样本示例（概念示意，非真实数据格式）：
messages: [
  {role: user, content: "这张图里有什么？<image>"},
  {role: assistant, content: "图中是一只橘猫坐在窗台上。"}
]
images: ["/path/to/cat.jpg"]

编码时：<image>占位符被替换为该图片经过 ViT+Aligner 处理后的一串视觉Token
```

**Grounding（视觉定位）任务**是这一数据格式的一个重要扩展场景——模型不仅要"看懂"图像，还需要输出图像中特定物体的**边界框坐标**，这需要在数据格式中额外增加坐标相关字段，并且训练时需要有专门的编码方案把坐标数值转换为模型能生成的Token形式（不同模型对坐标的Token化约定不同，如归一化到 0-1000 的整数区间再当作普通数字Token生成，或使用专门设计的坐标特殊Token），这部分内容随附 ms-swift 文档第 17 章有更具体的实现层面讨论，可作为深入参考。

## 11.4 视觉输入的分辨率与计算量权衡

图像/视频输入的分辨率直接决定其被切分成多少个视觉Token，进而直接影响计算与显存开销——这是多模态训练区别于纯文本训练的一个特有工程维度。对于视频类输入，还需要额外权衡"抽帧频率"（每秒抽取多少帧参与训练）与"单帧分辨率"这两个相对独立的旋钮：**降低抽帧数量能减少总Token量但可能损失时序信息（不利于需要理解动作/事件先后顺序的任务）；降低单帧分辨率保留了更多帧但牺牲了每帧的细节（不利于需要精细视觉识别的任务，如OCR）**，具体权衡需要结合任务性质决定。这一权衡在随附 ms-swift 文档第 17 章的 MAX_PIXELS 体系讨论中有详细展开，其中特别提到的"训练与推理阶段需要保持分辨率处理方式一致，否则会导致分布不一致"这一工程细节，是多模态训练实践中一个高频踩坑点，值得格外留意。

## 11.5 混合调优在多模态场景的应用

第 7 章介绍的"混合调优"（不同模块采用不同训练策略）在多模态场景下的典型应用，就是**对 ViT、Aligner、LLM 三部分分别独立设置冻结/训练策略**：一个常见的资源受限场景下的实践组合是"冻结 ViT（因为预训练视觉编码器通常已具备良好的通用视觉特征提取能力）+ 适当限制输入分辨率（降低视觉部分计算开销）+ 对 LLM 部分使用 LoRA"；而如果任务本身对视觉理解精度要求很高（例如需要学习全新的、预训练阶段未见过的图像风格），则可能需要对 ViT 部分做全参数训练，此时训练成本会显著上升。这部分决策逻辑与具体实现细节，随附 ms-swift 文档第 17 章已有充分展开，建议直接参照。

## 11.6 多模态场景下的位置编码：M-RoPE

第 2 章提到，多模态场景的位置编码需要额外设计——以 Qwen-VL 系列采用的 **M-RoPE（多模态旋转位置编码）**为例，其核心思路是把原本纯文本场景下"一维的序列位置"，扩展为同时编码"时间、宽、高"等多个维度的位置信息，使得模型能够更好地理解视觉内容内部的二维空间结构（对图像而言）以及跨帧的时间结构（对视频而言），而不是把图像简单"拍扁"成一维Token序列后丢失空间结构信息。

## 11.7 多模态 Packing 的额外挑战

第 3 章介绍的 Packing 技术在多模态场景下收益尤为显著（随附 ms-swift 文档提到的"训练速度提升 100% 以上"的量化收益，正是源于多模态样本长度差异比纯文本场景更悬殊——部分样本含大量视觉Token、部分样本不含视觉输入）。但多模态 Packing 的实现挑战也更大：需要同时正确维护"文本Token边界"与"视觉Token边界"两套位置信息，确保拼接后不同原始样本的视觉特征不会通过注意力机制"泄漏"到其他被拼接的样本中；对使用 M-RoPE 这类复杂位置编码方案的模型而言，Packing 后的位置编码重新计算逻辑也更复杂。

## 11.8 本章小结与学习建议

多模态训练本质上是"在纯文本大模型的知识体系基础上，额外理解一层'如何把其他模态转换为Token'的转换机制"，不需要把它当作一个完全独立的新领域重新学习——第 2-10 章介绍的绝大部分概念（Tokenizer、分布式并行、PEFT、对齐训练、评测方法论）在多模态场景下依然成立，只是需要叠加理解本章介绍的这几个多模态特有的设计维度。

推荐资料：CLIP 论文（理解视觉-语言对齐预训练的奠基性工作）、LLaVA 系列论文（"三段式"多模态架构范式的代表性开源工作，公开程度高，适合作为入门精读对象）、Qwen-VL 系列技术报告（M-RoPE 与动态分辨率策略的一手资料）；随附 ms-swift 文档第 17 章可作为"具体框架如何落地这些概念"的深入案例研究直接参照。

# 第 12 章　推理部署与训练的衔接

## 12.1 为什么推理背景的人需要重新审视这一章

如果你来自推理/应用背景，本章的很多概念你可能并不陌生（KV Cache、量化、批处理调度），但本章的目的不是重新科普这些概念本身，而是建立**"这些推理侧概念，如何与训练侧的决策相互影响"**这一双向因果链条——这正是第 1 章提到的"训练与推理形成双向反馈"这一心智转变在技术细节层面的落地。

## 12.2 从训练产出到可服务模型：完整链路

```
训练产出的 Checkpoint
（全参数训练：完整模型权重；PEFT训练：Base模型 + LoRA适配器权重）
        │
        ▼
┌───────────────────┐
│  权重合并 (Merge)    │  若是LoRA/QLoRA训练，通常需要将适配器权重与Base模型合并，
│  （PEFT场景需要）      │  得到一份结构与原始Base模型完全一致的完整权重（第7章已提及）
└─────────┬──────────┘
          ▼
┌───────────────────┐
│  量化 (Quantization) │  （可选）为降低推理显存占用/提升吞吐，将权重转换为低比特表示
└─────────┬──────────┘
          ▼
┌───────────────────┐
│  推理引擎加载部署      │  transformers（保底通用）/ vLLM / SGLang / LMDeploy 等
└─────────┬──────────┘
          ▼
     对外提供服务（通常封装为OpenAI兼容API）
```

随附 ms-swift 文档第 10、11 章分别对"推理引擎抽象与多后端统一封装"和"部署、量化与模型导出"有具体实现层面的详细分析，本章聚焦这条链路上，与训练侧决策直接相关的几个关键衔接点。

## 12.3 KV Cache：推理侧的核心概念，如何反向影响训练侧设计

**KV Cache 是什么**：自回归生成时，每生成一个新Token，都需要用到之前所有位置在注意力计算中产生的 Key 和 Value 向量；如果每生成一个新Token都重新计算一遍之前所有位置的 K、V，会造成大量重复计算，KV Cache 的做法是**把已经计算过的 K、V 缓存下来，后续生成新Token时只需要计算新Token自己的 K、V，与缓存中的历史 K、V 一起参与注意力计算**，是让自回归生成变得高效可行的核心工程技术。

**这如何反过来影响训练侧的架构选择**：第 2 章提到的 GQA/MQA（多个 Query 头共享同一组 Key/Value 头）设计，其核心动机正是**为了降低推理时 KV Cache 的显存占用**（KV Cache 的大小与 KV 头的数量直接成正比）——这是一个"推理侧的效率需求，反向驱动了训练侧模型架构设计选择"的典型例证，理解这层因果关系，有助于理解为什么现代大模型在预训练阶段就要提前确定采用 GQA 这类架构决策，而不是训练完之后才考虑推理效率问题。

## 12.4 量化：从训练侧到推理侧的多个层次

量化技术在整条训练-推理链路中，实际出现在多个不同的层次，容易混淆，有必要做区分：

| 应用层次 | 技术代表 | 目的 |
|---|---|---|
| 训练时的混合精度 | FP16/BF16（第2章已介绍） | 加速训练计算、降低训练显存占用，训练结束后模型权重通常仍以BF16等较高精度保存 |
| PEFT训练时的权重量化 | QLoRA 的 4-bit 量化（第7章已介绍） | 在训练阶段就降低被冻结的Base模型权重的显存占用，让资源受限场景下的训练成为可能 |
| 训练完成后、面向推理部署的量化 | GPTQ、AWQ、BnB、FP8（本章讨论对象） | 降低推理时的显存占占用与提升推理吞吐速度，是"训练结束之后"的独立后处理步骤 |

**推理侧量化技术简述**：GPTQ 与 AWQ 都是训练后量化（Post-Training Quantization, PTQ）方法，核心思路是利用少量校准数据，找到对模型输出影响最小的量化方式（而非简单粗暴地把每个权重四舍五入到最近的低精度表示），二者的具体算法细节差异（如 AWQ 侧重于保护"对激活值影响较大的少数关键权重通道"不被过度量化）超出本手册范围，建议在实际需要选型时查阅对应论文。**FP8** 则依赖较新硬件架构（如 NVIDIA Hopper 架构）的原生数值支持，随附 ms-swift 文档第 18 章提到的"量化技术选型必须结合目标部署硬件平台"这一原则，正是理解 FP8 适用边界的关键出发点——量化方案的选型从来不是一个孤立的"哪种精度损失更小"问题，而是必须结合目标推理硬件平台能力的联合决策。

## 12.5 Continuous Batching：推理引擎的核心调度技术，为何训练背景的人容易低估其重要性

传统小模型推理/训练背景的人，习惯的批处理方式是"固定 Batch Size，所有样本一起进、一起出"；但大模型推理场景下，不同请求的生成长度差异巨大（有的请求生成几个Token就结束，有的需要生成上千个Token），**Continuous Batching（连续批处理）** 允许在一个 Batch 内，某个请求提前结束后，立即让新的请求"插队"补入这个 Batch 继续处理，而不必等待Batch内所有请求都结束才统一开始下一批——这一调度技术是 vLLM/SGLang 等现代推理引擎相比朴素实现能大幅提升吞吐量的核心原因之一。理解这一技术，对理解第 8 章提到的"为什么 RLHF/GRPO 训练要把专门的推理引擎集成进 Rollout 环节，而非用训练框架自带的朴素生成逻辑"这一设计决策至关重要——朴素生成逻辑在处理"同一批Prompt生成长度差异巨大"这一典型 RL 采样场景时，效率损失会非常显著。

## 12.6 从推理侧反哺理解训练侧的一个具体案例：Reward Hacking 与生成长度

第 8 章提到 Reward Hacking 的一个常见表现是"模型学会通过增加回答长度来骗取奖励模型的高分"。如果具备推理侧的知识背景，会更容易理解这一现象为何在工程上格外值得警惕——**更长的生成结果，意味着更多的 KV Cache 显存占用、更长的生成延迟、更高的服务成本**，一个在对齐训练阶段"悄悄变啰嗦"的模型，会在推理部署阶段直接以更高的服务成本和更差的用户体验形式体现出来，这是训练侧的一个看似"只影响模型行为"的问题，实际上有着直接、可量化的推理侧代价。

## 12.7 本章小结与学习建议

推理与训练之间不是"先训练完、再交给推理团队部署"这样简单的单向流水线关系，而是在架构设计（GQA/MQA）、训练算法本身的执行方式（RLHF/GRPO 的 Rollout）、以及行为质量的实际代价（Reward Hacking 的服务成本影响）等多个层面存在双向的相互塑造关系。建议具备推理背景的读者，重点巩固"训练侧决策为什么会这样做"的原理理解（第 2、5-8 章）；建议训练背景的读者，重点补齐"推理侧的效率约束具体是什么、如何反过来影响训练侧的设计选择"这一视角（本章内容）。

推荐资料：论文 "Efficient Memory Management for Large Language Model Serving with PagedAttention"（vLLM 的核心论文，理解 KV Cache 管理与 Continuous Batching 调度的一手资料）；GPTQ/AWQ 原始论文；随附 ms-swift 文档第 10、11 章（具体框架如何统一封装多种推理后端、如何组织量化与导出流程的落地案例）。

# 第 13 章　硬件与集群工程

## 13.1 为什么大模型训练工程师需要懂一些硬件知识

传统小模型训练，工程师往往只需要把硬件当作"一个提供算力的黑箱"；大模型训练场景下，由于分布式并行（第6章）对通信效率高度敏感，**硬件拓扑结构本身会直接影响并行策略的设计与实际训练效率**，不了解基本的硬件与网络知识，很难对训练效率异常做出准确判断，也很难合理规划资源预算。

## 13.2 GPU 显存与算力的基本认知

不同代际、不同型号的 GPU，核心差异体现在三个维度：**显存容量**（决定单卡能装下多大的模型/多长的序列/多大的Batch）、**算力（FLOPs）**（决定计算速度）、**显存带宽**（决定数据在显存与计算单元之间搬运的速度，很多大模型训练场景实际上是"显存带宽受限"而非"算力受限"，这也是为什么单纯堆砌算力型号、而不匹配相应的显存带宽，实际训练吞吐提升可能不及预期）。

## 13.3 机内高速互联：NVLink 与 PCIe

同一台物理机内的多张 GPU 之间，通信方式主要有两种：**PCIe**（通用总线，带宽相对有限）与 **NVLink**（NVIDIA 专有的高速互联技术，带宽远高于 PCIe，专为多GPU协同计算设计）。第 6 章提到"张量并行/序列并行因为通信频率极高，通常只适合安排在机内高速互联的卡之间"，正是因为这些并行策略对通信带宽的要求，只有 NVLink 级别的带宽才能较好满足，PCIe 级别的带宽用于这些高频通信场景会成为明显的效率瓶颈。

## 13.4 机间网络互联：InfiniBand 与 RoCE

当训练规模扩展到多台物理机（多机多卡）时，机器之间的网络互联质量成为决定分布式训练效率的关键因素。**InfiniBand（IB）** 是数据中心高性能计算领域的传统高速网络技术，**RoCE（RDMA over Converged Ethernet）** 则是在更通用的以太网基础设施上实现类似 RDMA（远程直接内存访问，允许跨机器直接读写对方内存而不经过CPU中转，大幅降低通信延迟）能力的方案，二者都远快于普通数据中心网络。第 6 章提到"流水线并行的通信相对稀疏、可以跨机器安排，数据并行的通信频率最低、最适合大规模跨机扩展"，这些结论的前提正是机间网络本身具备相应的高速互联能力——如果机间网络质量很差，即便是"通信频率较低"的并行维度，跨机扩展的效率损失也会显著增加。

## 13.5 存储系统对训练数据流水线的影响

预训练数据集动辄 TB 到 PB 级别，训练过程中数据需要持续、高吞吐地从存储系统读取并送入 GPU 计算——如果存储系统的读取吞吐跟不上 GPU 的计算消耗速度，会导致"GPU 利用率不足、大量时间在等待数据"这一常见的效率问题（第10章提到的"GPU利用率指标"正是用于发现这类瓶颈）。大规模训练场景通常需要专门的分布式高吞吐存储系统（如并行文件系统）配合，而非依赖普通的单机磁盘或通用对象存储。

## 13.6 训练任务调度：Slurm 与 Kubernetes

大规模集群上运行训练任务，通常依赖专门的任务调度系统管理计算资源的分配与任务排队：**Slurm** 是高性能计算（HPC）领域的传统任务调度系统，在学术界与很多大模型训练团队中广泛使用；**Kubernetes（K8s）** 则是云原生领域的容器编排事实标准，近年也越来越多地被用于管理大规模 AI 训练任务（通常配合专门的AI训练相关扩展组件）。理解这两套生态各自的定位，对于评估一个团队/云平台的训练基础设施成熟度会有帮助，但具体使用方式属于运维/基础设施工程范畴，本手册不做展开。

## 13.7 容错与弹性训练

大规模、长周期的训练任务，遇到硬件故障（某张卡/某台机器突然宕机）的概率会随着规模和时长的增加而显著提升——这是预训练这类数周甚至数月连续运行任务必须面对的现实问题。核心应对手段包括：**定期 Checkpoint**（以一定频率保存完整的训练状态，一旦发生故障可以从最近的检查点恢复而非从头重跑，代价是过于频繁的 Checkpoint 本身会占用额外的存储与I/O开销，需要权衡checkpoint频率与故障恢复代价）；**弹性训练（Elastic Training）**（训练任务能够在检测到部分节点故障后，动态调整并行策略配置、用剩余的健康节点继续训练，而不是整个任务直接崩溃终止，是应对超大规模长周期训练任务的重要工程能力，第9章提到的部分底层分布式引擎已开始提供相应支持）。

## 13.8 训练成本的粗略估算方法

一个粗略但实用的成本估算直觉框架（用于快速判断一个训练任务的资源需求量级，而非精确预算）：

```
所需总计算量 (FLOPs)  ≈  常数 × 模型参数量 × 训练Token数量
（这一比例关系正是第5章提到的 Scaling Law 的直接应用之一）

所需GPU数量 × 训练时长  ≈  所需总计算量 / 单卡有效算力（需考虑实际利用率折损，
                          实际大规模分布式训练的有效算力利用率通常在理论峰值的
                          30%-60%左右，而非100%，这一折损主要来自通信开销、
                          流水线气泡、数据加载等因素，第6、10章已分别讨论过这些因素）
```

这一估算框架的实践价值在于：帮助工程师在项目立项阶段，快速判断"这个训练任务大致需要多少GPU、跑多久"，从而评估资源可行性，而不必等到实际投入资源跑起来之后才发现规模严重超出预算。

## 13.9 国产算力生态：一个值得关注的趋势

随附 ms-swift 文档第 18 章对硬件适配这一主题做了详细的专题分析，其中提到的"硬件支持矩阵从单一NVIDIA GPU扩展到Ascend NPU、AMD GPU（ROCm生态）、MetaX等多元算力平台"这一趋势，反映了当前大模型训练领域一个值得持续关注的产业动向——**训练框架与硬件生态的适配工作，正在从"NVIDIA 生态独大"逐步走向"多元硬件平台并存"**。对于希望深入这一方向的读者，该文档提出的几条实践建议具有相当的普适性（不局限于ms-swift这一个框架）：硬件切换的成本评估需要同时覆盖训练与推理两端；分布式训练后端与硬件平台的组合需要单独验证性能特征，不能想当然地线性外推；量化方案的选型必须结合目标部署硬件平台。

## 13.10 本章小结与学习建议

硬件与集群工程是大模型训练领域"工程深度最深、但入门所需先验知识相对独立"的一个方向——即便不深入这一方向，也不妨碍在中小规模场景下做好数据工程、微调、对齐等工作；但如果职业方向明确指向"大规模预训练/超大规模训练基础设施"这一细分领域，本章内容值得进一步系统深入学习。

推荐资料：随附 ms-swift 文档第 9、18 章（分布式并行与硬件适配的具体案例分析）；NVIDIA 官方关于 NVLink/InfiniBand 的技术文档；"The Ultra-Scale Playbook"（第6章已推荐，同样覆盖了硬件拓扑与并行策略匹配的相关内容）；各大模型技术报告（如LLaMA、DeepSeek系列）中通常会披露的训练集群规模、硬件配置与训练效率（MFU，Model FLOPs Utilization，即实际有效算力利用率）等一手数据，是理解真实工业级训练资源投入量级的宝贵参考。

# 第 14 章　学习路径规划

## 14.1 规划学习路径的基本原则

前面 13 章建立起的是"知识地图"，本章要解决的是"按什么顺序、以什么节奏，把这张地图真正走一遍"这一实操问题。建议遵循三条基本原则：**原理先行，工具随后**（先理解第2、5-8章的原理性内容，再动手学习具体框架的使用，避免陷入"会调用API但不理解为什么这么设计"的浅层学习状态）；**小规模实践优先于大规模理论学习**（很多分布式训练、对齐训练的直觉，只有亲手跑过实验、观察过真实的训练曲线和资源占用之后才能真正建立，单纯读论文很难替代这一过程）；**分阶段推进，不追求一步到位**（大模型训练涉及的知识面极广，试图一次性系统学完所有内容容易导致效率低下甚至半途而废，分阶段、有优先级地推进更现实）。

## 14.2 按背景差异定制的学习路径起点（承接第1章）

**传统小模型训练背景**：第一阶段重点补齐"规模化工程"认知缺口——优先攻克第 6 章分布式训练（哪怕只是先在小规模上用 ZeRO/FSDP 跑通一次多卡训练），再补齐第 3 章数据工程的规模化处理方式（体验一次"清洗+去重+格式转换"的简化流水线）。

**大模型推理/应用背景**：第一阶段重点补齐"训练内部机制"认知缺口——优先攻克第 2 章训练动力学基础与第 10 章训练监控方法论，再进入第 7 章 SFT/PEFT 实践（这是投入产出比最高、最容易建立"训练手感"的实践环节）。

## 14.3 建议的四阶段学习节奏（以全职投入为参照，兼职学习者可按比例延长）

### 第一阶段（约 2-4 周）：建立知识地图与基础理论

目标：完成本手册第 1-4 章内容的通读与理解，配合第 2 章推荐的课程（斯坦福 CS336 强烈建议作为这一阶段的主线课程）与"The Illustrated Transformer"等可视化资料，确保对 Transformer 架构、Tokenizer、训练目标形式建立扎实理解，不留术语盲区。

产出验收标准：能够不看资料，用自己的语言向别人讲清楚"预训练/SFT/RLHF 分别在解决什么问题、训练目标有什么本质区别"，以及"BPE 分词的基本原理"。

### 第二阶段（约 4-8 周）：动手实践 SFT/PEFT，建立训练手感

目标：选定一个开箱即用的一站式框架（本手册建议以 ms-swift 为主力工具，因为随附文档已提供了深入的架构参考），在一张消费级/云上按需 GPU 上，完成至少 2-3 次完整的 LoRA/QLoRA 微调实验（可以是不同的开源模型、不同的任务数据集），过程中重点练习：如何准备 SFT 数据格式、如何观察训练曲线判断是否正常、如何在微调前后对比模型的实际回答质量变化。

产出验收标准：能够独立完成"选定开源Base模型 → 准备/清洗一份SFT数据集 → 配置并启动LoRA微调 → 监控训练过程 → 评估微调后效果"这一完整闭环，不需要依赖他人手把手指导。

### 第三阶段（约 4-8 周）：深入分布式训练与对齐训练

目标：在第二阶段的基础上，一方面尝试更大规模的训练任务（引入多卡分布式，体验 ZeRO/FSDP 的实际配置与效果），另一方面学习并实践 DPO（工程门槛相对较低，是进入对齐训练领域的最佳起点），有条件的话进一步尝试 GRPO（可以先在一个有明确对错标准的小任务，如简单数学题，用规则化奖励做实验，规避训练一个独立奖励模型的额外复杂度）。

产出验收标准：理解并能够解释第6章介绍的各类并行策略分别解决什么问题；完成至少一次 DPO 训练实验，并能够解释训练数据格式与朴素 SFT 的本质区别。

### 第四阶段（长期持续）：跟踪前沿、深入细分方向、建立评测与调试经验

目标：这一阶段不再有明确的"学完"终点，而是转向持续跟踪领域最新进展（尤其是对齐训练方向，如第8章提到的，是当前论文更新最快的领域）、根据实际工作/研究方向深入某个细分领域（可能是多模态、可能是超大规模预训练工程、可能是特定垂直领域的对齐技术），并在实践中持续积累第10章提到的"训练问题排查经验库"。

## 14.4 学习资源的分层使用建议

不同类型的学习资源，适合承担不同的学习功能，建议有意识地区分使用：

| 资源类型 | 适合承担的学习功能 |
|---|---|
| 系统性课程（如CS336） | 建立结构化的知识框架，尤其适合第一阶段 |
| 论文原文 | 深入理解某个具体技术的设计动机与实验证据，适合"确定了要深入某个方向"之后精读 |
| 框架官方文档/架构分析文档（如随附的ms-swift文档） | 理解"概念如何在具体工程中落地"，是连接理论与实践的桥梁 |
| 开源项目代码（如nanoGPT、TRL） | 建立对"训练循环具体是怎么写出来的"的具体认知，适合有一定基础后，希望进一步降低"黑箱感"时阅读 |
| 技术报告（如各大模型发布时附带的Technical Report） | 获取工业界一手实践经验与真实资源投入数据，是理解"学术论文中的方法，在真实大规模场景下效果与代价如何"的重要信息源 |
| 社区讨论（如相关技术社区、论坛、问答平台） | 获取实践中的具体报错排查经验、框架选型的真实用户反馈，适合遇到具体问题时检索参考 |

## 14.5 一个常见的学习误区：过度追求"从零手写一切"

有些学习者会陷入"必须自己从零手写一遍Transformer、从零手写一遍分布式通信逻辑，才算真正理解"这一执念，这在时间投入上并不划算——**理解原理与亲手实现每一行代码是两回事**，第6章反复强调的正是"理解并行策略解决什么问题、有什么权衡"这一原理层面的认知比记住具体实现细节更重要。合理的实践深度是：亲手完成过"用现成工具跑通一次完整训练流程"这一层级的实践（第二、三阶段的核心要求），而非要求自己达到"能够重新发明一个训练框架"这一不必要的深度，除非你的职业方向明确是"训练框架本身的研发"这一细分领域。

## 14.6 本章小结

学习路径规划的核心是"先建立地图、再动手实践、逐步深入、长期跟踪"这一节奏，不同背景的学习者应该根据自己的知识空白调整起点与重心分配，但最终都应该走向"具备完整的知识地图 + 至少一次完整的实践闭环经验 + 持续学习的能力"这一共同终点。下一章作为全书收尾，给出具体的实战项目建议与完整的资源清单汇总。
# 第 15 章　实战路线图与资源大全

## 15.1 循序渐进的实战项目路线图

本节给出一条具体的、按难度递增排列的实战项目建议，每个项目都对应前面章节的知识点，建议按顺序推进（但不要求每个项目都做到极致完美，"跑通并理解发生了什么"比"做到最优效果"更重要）。

### 项目一：复现 nanoGPT 级别的小规模预训练（对应第2、5章）

在单卡（消费级显卡即可）上，用一个小规模数据集（如莎士比亚文集这类几MB级别的文本）从零训练一个几百万到几千万参数级别的小型 GPT 模型。这个项目的价值不在于练出一个"有用"的模型，而在于**亲手走一遍"Tokenizer构建 → 数据构造 → 模型定义 → 训练循环 → 生成采样"的完整闭环**，建立起对"预训练到底在做什么"最直观、最没有框架黑箱遮蔽的理解。

### 项目二：在开源 Base 模型上做一次 LoRA/QLoRA 微调（对应第3、4、7章）

选定一个中等规模（如 7B 左右）的开源 Base 模型，选定一个具体任务（如特定风格的对话、特定领域的问答），完成"准备/清洗SFT数据 → 用QLoRA在单卡上微调 → 对比微调前后模型表现"的完整流程。这一项目建议使用 ms-swift 或 LLaMA-Factory 这类一站式框架完成，把精力集中在"数据准备是否得当、微调效果是否符合预期"这些更本质的问题上，而非底层实现细节。

### 项目三：多卡分布式训练实践（对应第6章）

在能够获取多张GPU资源的条件下（云上按需租用即可），把项目二的任务规模适当放大（更大的模型或更大的数据量），实际配置并观察 ZeRO/FSDP 数据并行训练的效果，重点观察：显存占用如何随并行策略配置变化、训练吞吐量（Tokens/秒）如何随卡数增加而变化（是否接近线性提升，还是存在明显的通信开销损耗）。

### 项目四：DPO 对齐训练实践（对应第8章）

准备或使用开源的偏好数据集（包含"更优回答/更差回答"成对样本），在项目二微调得到的 SFT 模型基础上，完成一次 DPO 训练，对比 DPO 前后模型在开放式问答质量上的主观差异。

### 项目五：规则化奖励的 GRPO 实践（对应第8章）

选定一个有明确对错标准的小任务（如小学数学应用题，可直接复用 GSM8K 这类公开数据集的问题部分），设计一个简单的规则化奖励函数（如"提取模型生成答案中的最终数值，与标准答案比对是否一致"），完成一次 GRPO 训练实验，观察模型在该任务上的准确率是否随训练提升，并留意是否出现第8章提到的 Reward Hacking 迹象（如模型学会输出多个候选答案"广撒网"而非真正给出确定唯一的解题过程）。

### 项目六（进阶，可选）：多模态微调实践（对应第11章）

选定一个开源的中等规模多模态模型，用一个视觉问答类数据集完成一次多模态 SFT 微调，重点体验第11章提到的"视觉Token占位符、混合调优三段式控制"这些多模态特有的工程概念。

### 项目七（进阶，可选）：端到端跑通一次标准化评测（对应第10章）

对项目二至项目五中产出的任意一个模型，使用 EvalScope/OpenCompass/lm-evaluation-harness 中的任意一个标准化评测工具，在至少一个客观评测基准（如GSM8K）和一个主观评测基准（如需要LLM-as-a-Judge的开放对话评测）上完成打分，体验"客观评测"与"主观评测"在方法论上的差异。
